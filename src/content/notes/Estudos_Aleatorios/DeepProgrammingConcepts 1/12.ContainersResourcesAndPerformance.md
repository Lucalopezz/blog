# Containers, resource limits, and performance reasoning

## A container is isolated processes, not a VM

A Linux container normally consists of regular host-kernel processes with:

- namespaces controlling what they can see (PIDs, mounts, network, hostname, users, IPC);
- cgroups controlling/accounting resources (CPU, memory, I/O, process count);
- capabilities and security policies limiting privileged actions;
- a packaged filesystem and configuration.

```text
host hardware
└── one host kernel
    ├── host processes
    ├── container A processes + namespaces/cgroup
    └── container B processes + namespaces/cgroup
```

A hardware VM usually runs another guest kernel over virtualized hardware. CPU virtualization extensions help guests execute safely and efficiently, but the hypervisor still mediates privileged state and devices.

The distinction matters: a Linux container needs a compatible Linux kernel; it does not carry its own. Container isolation is useful but generally not identical to a strong VM boundary.

## Limits change what the runtime should believe

A process may see many host CPUs while its cgroup grants only a fraction of their time. It may see host memory information while facing a much smaller cgroup limit. Modern runtimes increasingly detect this, but verify yours.

Consequences:

- a thread pool sized to host CPUs can oversubscribe its quota;
- a heap sized from host RAM can be OOM-killed inside a small limit;
- per-thread stacks/allocator arenas become costly at high thread counts;
- filesystem and network I/O can be throttled independently of CPU.

Useful cgroup v2 observations on Linux:

```bash
cat /sys/fs/cgroup/cpu.max
cat /sys/fs/cgroup/memory.max
cat /sys/fs/cgroup/memory.current
cat /sys/fs/cgroup/memory.events
cat /sys/fs/cgroup/pids.max
```

`memory.events` can reveal a cgroup OOM. Exit code 137 often means termination by `SIGKILL`, but it does not prove OOM without surrounding evidence.

## Images solve packaging, not every dependency

An image can fix user-space files, libraries, runtime, and application code. It does not freeze:

- the host kernel and CPU features;
- runtime resource availability/noisy neighbors;
- external databases, queues, DNS, certificates, and APIs;
- persistent data formats;
- clock and network behavior.

Pin image digests for reproducibility, rebuild for security updates, use multi-stage builds to keep build tools out of runtime images, and run as a non-root identity where practical. A single static binary can simplify the image but still has OS/architecture and external-data assumptions from [[2.CompilingLinkingAndLoading]].

## Signals and PID 1

The container's main process is PID 1 in its PID namespace. PID 1 has special signal/orphan-reaping responsibilities on Linux. Shell-form entrypoints can accidentally consume signals instead of forwarding them.

Applications should handle `SIGTERM`, stop accepting work, drain with a deadline shorter than the orchestrator's grace period, and exit. Forced `SIGKILL` skips cleanup.

## Performance is queueing plus resources

Four metrics answer different questions:

- **throughput**: completed work per second;
- **latency**: time per operation, especially percentiles;
- **utilization**: fraction of resource capacity occupied;
- **saturation**: queued work waiting for capacity.

At high utilization, small service-time variability can cause large queueing latency. “CPU is only 70%” may hide one saturated core, a quota throttling period, lock contention, disk queue, connection-pool wait, or event-loop stall.

For a service request, sketch the wait chain:

```text
load balancer queue
  ► app runnable queue / event loop
  ► connection pool
  ► database locks and I/O
  ► response socket buffer
```

Measure each boundary. End-to-end latency without queue/resource metrics tells you that the system is slow, not why.

## A disciplined investigation order

1. Reproduce or capture a production profile under representative load.
2. Check errors, timeouts, restarts, OOM events, and throttling.
3. Identify the saturated resource or queue.
4. Separate CPU time, off-CPU wait, allocation/GC, lock wait, and I/O.
5. Change one bottleneck, then rerun the same measurement.

Commands that establish a first picture:

```bash
ps -eo pid,ppid,nlwp,stat,pcpu,rss,vsz,comm --sort=-pcpu
vmstat 1
pidstat -durw -p <pid> 1
ss -s
```

Then use application metrics, tracing, profiles, runtime-specific diagnostics, and database/queue telemetry.

## Common misleading conclusions

- **“More workers make it faster.”** Only until a CPU, lock, connection pool, or downstream service saturates.
- **“Async is faster.”** It often improves concurrency/throughput for waiting workloads; it adds overhead and does not accelerate CPU work.
- **“Free memory is wasted memory.”** The OS uses available RAM for page cache; reclaimable cache is not the same as application exhaustion.
- **“A high RSS proves a leak.”** It may be live data, retained allocator/GC heap, shared mappings, or fragmentation. Use [[9.VirtualMemoryPagingAndSwap]] and [[11.GarbageCollectionAndOwnership]].
- **“The technology that handled millions of connections will scale my product.”** Architecture follows workload, constraints, failure semantics, team knowledge, and cost—not an isolated benchmark.

The recurring lesson across the videos is strongest when made operational: know which layer owns each resource, inspect real state, and optimize the measured constraint.

# Threads, scheduling, and synchronization

## What a thread owns and shares

A thread is an execution context inside a process. Each thread has its own program counter, registers, stack, scheduling state, and usually thread-local storage. Threads in one process share the address space, code, heap, and open resources.

```text
process
├── shared: code, globals, heap, file descriptors
├── thread A: registers + stack A
├── thread B: registers + stack B
└── thread C: registers + stack C
```

This explains both sides of threads: communication through shared memory is cheap, while accidental interference is easy.

## Scheduling and context switches

An OS scheduler chooses a runnable thread for each logical CPU. Preemptive scheduling uses timer interrupts and other events to regain control even if a thread never volunteers to yield. A context switch saves one thread's architectural state and restores another's.

The cost is more than saving registers. Switching may disturb caches, TLB entries, branch predictors, and locality. A thread that migrates to another core can lose warm private caches. Still, context switching is normal; the mistake is creating far more runnable work than the machine or downstream resources can use.

Thread states, simplified:

```text
             scheduled
runnable ───────────────► running
   ▲                        │
   │ wakeup                 │ wait / blocking I/O / lock
   │                        ▼
   └──────────────────── blocked
```

A blocked thread does not consume a CPU time slice, but retains resources such as its stack and kernel metadata.

## Concurrency is not parallelism

- **Concurrency**: multiple tasks can be in progress during overlapping time.
- **Parallelism**: multiple tasks execute at the same physical instant.

One core can interleave concurrent tasks. Multiple cores allow parallel execution. SMT/“hyper-threading” exposes multiple logical CPUs from one physical core, but they share execution resources and do not equal independent cores.

For a fuller workload model, see [[6.ConcurrencyParallelismAndAsyncIO]].

## A race is about missing ordering

Assume two threads execute `counter++`. At machine level it is conceptually read, add, write:

```text
counter = 10

Thread A: read 10 ─ add 1 ───── write 11
Thread B: ── read 10 ─ add 1 ─ write 11

Expected 12; observed 11.
```

The high-level expression is not necessarily atomic. A **data race** has conflicting accesses to the same memory, at least one write, without required synchronization. A broader **race condition** is any result that incorrectly depends on timing, including races across processes or services.

CPU and compiler reordering make “it worked in my test” especially weak evidence. Language memory models define which values become visible across threads and what synchronization establishes a **happens-before** relationship.

## Synchronization tools

- **Mutex**: one owner enters a critical section at a time. Protect an invariant, not an arbitrary line.
- **Read-write lock**: concurrent readers or one writer. It helps only for suitable read-heavy contention patterns.
- **Semaphore**: permits up to N concurrent holders; useful for limiting a scarce resource.
- **Condition variable**: allows waiting for a state predicate while atomically releasing/reacquiring a mutex.
- **Atomic operation**: indivisible operation with specified memory-order semantics. Good for counters and carefully designed lock-free algorithms, not a universal mutex replacement.
- **Barrier/latch**: coordinates phases or completion among several participants.

Correct condition-variable shape:

```c
lock(mutex);
while (!condition_is_true())      // while, not if: wakeups can be spurious
    wait(condition, mutex);       // atomically unlocks and sleeps
use_state_protected_by_mutex();
unlock(mutex);
```

## Deadlock and liveness

Classic deadlock requires four conditions: mutual exclusion, hold-and-wait, no forced resource removal, and a cycle of waiting. A common prevention rule is a global lock order:

```text
always acquire: account_lock -> ledger_lock
never acquire:  ledger_lock -> account_lock
```

Other failures:

- **Livelock**: threads keep reacting but no useful work completes.
- **Starvation**: one participant repeatedly loses access to a resource.
- **Priority inversion**: a high-priority thread waits on a lock held by a lower-priority one.
- **Lock convoy**: many threads serialize behind a contended lock and repeatedly wake/sleep.

## How many threads?

There is no universal “one thread per core” rule.

- CPU-bound independent work usually benefits from roughly the available CPU parallelism, considering container quotas and other processes.
- I/O-bound work may tolerate more tasks because many wait, but platform threads still consume memory and scheduling resources.
- A resource pool must reflect the constrained downstream system. Fifty CPU workers backed by ten database connections do not create fifty-way progress.

Use bounded executors, queues, semaphores, or structured concurrency. Measure queue delay, runnable threads, context switches, CPU saturation, and downstream latency. The goal is completed useful work, not maximum thread count.

## Debugging practice

```bash
ps -L -p <pid> -o pid,tid,psr,stat,pcpu,comm
top -H -p <pid>
pidstat -w -p <pid> 1       # context-switch rates, if sysstat is installed
```

Thread sanitizers (`-fsanitize=thread` in supported native toolchains), runtime race detectors such as `go test -race`, thread dumps, and stress tests with randomized timing are far more useful than staring at code and hoping.

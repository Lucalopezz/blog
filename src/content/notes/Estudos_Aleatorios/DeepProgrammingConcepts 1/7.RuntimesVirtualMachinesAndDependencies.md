# Runtimes, virtual machines, and dependencies

## The language is not the runtime

When asking how a language behaves, separate at least four layers:

```text
language semantics
    ↓ implemented by
compiler / interpreter
    ↓ assisted by
language runtime / GC heap (if present)
    ↓ runs against
OS ABI + CPU ISA
```

C often uses a relatively small runtime and libc. Go produces native machine code but includes a runtime with a scheduler, stack management, and GC. Java code generally targets JVM bytecode and depends on JVM services. JavaScript behavior differs between a browser and Node.js because the host supplies different APIs and concurrency facilities.

This is why “compiled versus interpreted” predicts little by itself. Startup, warmup, JIT decisions, allocation rate, library implementation, syscalls, and workload shape all matter.

## Virtual machines

A language VM defines an abstract instruction set and managed execution environment. Bytecode provides a stable target above machine code; each host needs a VM implementation for its CPU/OS.

Typical services include:

- bytecode verification and class/module loading;
- JIT or ahead-of-time compilation;
- garbage collection and object layout;
- exceptions, reflection, profiling, and debugging;
- threading or user-space task scheduling;
- native interoperability.

The VM is not a security boundary equivalent to an OS process unless the implementation explicitly supplies and enforces sandboxing. Code in the same VM often shares fate and memory.

## JIT trade-offs

A JIT can optimize from observed behavior: concrete receiver types, frequently taken branches, and hot call paths. It may inline speculatively and later **deoptimize** if an assumption becomes false.

```text
startup ─► interpretation/baseline code ─► profiling ─► optimized code
                                               └──────► deoptimization
```

Benchmarks must account for warmup and steady state. A short CLI may finish before expensive optimization pays back; a long-running server may benefit substantially. JIT code and profiling metadata also consume memory.

## Native boundaries

FFI/JNI/C extensions cross from managed code into native libraries. They can deliver mature functionality and speed, but introduce:

- ABI and platform coupling;
- memory ownership questions;
- thread-safety constraints;
- blocking calls invisible to a runtime scheduler;
- crashes that can terminate the entire process;
- objects pinned so a moving GC cannot relocate them.

The GIL discussed in the videos is partly an example of an implementation choosing a global coordination mechanism around object/runtime access. Do not generalize it to every language or even every implementation of one language.

## Dependency graphs

Applications reuse libraries; those libraries reuse others. The result is a directed graph, not a flat list.

```text
application
├── web-framework ─► parser 2.x
└── db-client ─────► parser 1.x
```

The resolver must decide whether versions can coexist, which constraints win, and what artifact to fetch. This is a graph/constraint problem. A lockfile freezes one solution; it does not make that solution secure forever.

Distinguish:

- **source dependency**: compiled with the project;
- **binary dependency**: loaded as precompiled code;
- **runtime dependency**: required only when executing;
- **build dependency**: required to produce the artifact;
- **system dependency**: supplied by the OS image/package manager.

## Versioning and compatibility

Semantic versioning communicates intent, not truth. A “patch” release can break behavior accidentally; a major release may preserve what you use. Compatibility has dimensions:

- source, binary, behavioral, wire-format, data/schema, and operational compatibility;
- backward compatibility (new reads/serves old);
- forward compatibility (old tolerates new).

Safe upgrades are a routine engineering loop: read release notes, update one coherent slice, run tests/static checks, inspect transitive changes, deploy gradually, observe, and preserve a rollback path.

## Environments and executable selection

`PATH` is an ordered list of directories searched for commands. The shell usually stops at the first match.

```bash
printf '%s\n' "$PATH" | tr ':' '\n'
command -v python
python --version
python -c 'import sys; print(sys.executable); print(sys.path)'
```

A version manager changes command resolution; a Python virtual environment also isolates Python package installation and interpreter metadata. Neither creates OS-level isolation. A container adds namespaces, cgroups, a filesystem view, and packaging conventions, but still shares the host kernel; see [[12.ContainersResourcesAndPerformance]].

## Diagnosing “works on my machine”

Capture facts rather than reinstalling randomly:

```bash
env | sort
uname -a
file ./app
ldd ./app
git rev-parse HEAD
```

Then compare build inputs, environment, architecture, dynamic libraries, configuration, permissions, network reachability, and external service versions. A container image can freeze many user-space inputs, but not CPU behavior, kernel version, resource pressure, or external systems.

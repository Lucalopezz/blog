

## O que é um Caso de Uso?

**Casos de uso** são documentos utilizados na etapa de **análise** para especificar requisitos e compreender **o que o sistema deverá fazer**. Cada caso de uso descreve uma sequência de passos de um processo realizado com o sistema. 

> O foco é descrever **o que acontece**, e não como será implementado. 
> Cada caso de uso narra um conjunto de passos de um processo de negócio automatizado pelo sistema.

---

## Atores

Um **ator** é uma entidade externa que interage com o sistema para atingir algum objetivo. Pode ser:

* uma pessoa;
* outro sistema;
* um dispositivo físico.

Existem dois tipos principais:

* **Ator primário:** utiliza diretamente o sistema para atingir um objetivo.
* **Ator secundário:** auxilia o ator primário ou o próprio sistema. 

### Exemplo da biblioteca

No empréstimo de livros:

* **Atendente:** ator primário, pois opera o sistema.
* **Leitor:** ator secundário, pois participa do processo, mas não opera diretamente o sistema. 

---

## Identificando Casos de Uso

Para encontrar casos de uso, analisamos os requisitos procurando **eventos importantes que geram uma interação entre ator e sistema**.

Um caso de uso pode atender vários requisitos e um requisito também pode participar de vários casos de uso. 

Exemplo:

```text
Identificar Leitor
Emprestar Livro
Devolver Livro
```

A relação entre requisitos e casos de uso pode ser registrada para garantir **rastreabilidade**, ajudando a verificar se os requisitos estão sendo atendidos. 

```text
R1. O sistema deve garantir que apenas leitores registrados possam utilizar os serviços da biblioteca. A identificação do leitor deve ser feita a partir de um cartão de número único, com foto, que deverá ser apresentado ao atendente. 

R2. O sistema deve permitir que um leitor apto empreste um ou mais livros, por um período de tempo que varia de uma semana a seis meses, dependendo do tipo de leitor (uma semana para estudantes de graduação, 15 dias para estudantes de pós-graduação e seis meses para docentes). 

R3. O sistema deve considerar o leitor como apto a emprestar livros se ele não possuir em seu poder exemplares com data de devolução vencida (menor do que a data atual), desde que o número de livros emprestados não ultrapasse o número máximo permitido, que depende do tipo do leitor (seis livros para estudantes de graduação, dez livros para estudantes de pós-graduação e 15 livros para docentes).

R4. O sistema deve permitir que o leitor devolva um ou mais livros em seu poder, fazendo com que o livro volte a ficar disponível na biblioteca.
```

## Descrição textual

Um caso de uso pode possuir:

### Formato resumido

Um pequeno texto descrevendo apenas o **cenário principal de sucesso**.

![[Pasted image 20260803100056.png]]
### Formato completo

Possui mais detalhes, como:

* ator principal = quem usa
* interessados e interesses = quem se importa e por quê
* pré-condições = o que precisa ser verdade antes
* pós-condições = o que deve ser verdade depois
* fluxo principal = caminho normal
* fluxos alternativos = exceções/variações

Um fluxo principal representa o caminho esperado da operação, enquanto os **fluxos alternativos** descrevem situações como erros ou exceções.

## Boas práticas

Ao escrever casos de uso:

* Use normalmente o **ator como sujeito** da ação.
* Mantenha os casos de uso pequenos e compreensíveis.
* Não escreva como se fosse um algoritmo ou pseudocódigo.
* **Não descreva tecnologia ou implementação.**
* Use linguagem simples e mantenha os mesmos termos para os mesmos conceitos.

# Diagrama de Casos de Uso

## 1. Assunto / Fronteira do sistema

O **assunto** representa o sistema que está sendo modelado.

Ele é desenhado como um **retângulo**, e os casos de uso ficam dentro dele.

Exemplo:

```text
+-----------------------------+
|        App Bancário         |
|                             |
|      (Verificar Saldo)      |
|      (Fazer Pagamento)      |
|      (Transferir Dinheiro)  |
|                             |
+-----------------------------+
```

A fronteira deixa claro o que está **dentro do escopo do sistema** e o que está fora. 

---

## 2. Atores

Os atores representam entidades externas que interagem com o sistema.

Eles ficam **sempre fora da fronteira**.

```text
 Cliente

   O
  /|\
  / \
```

Não precisam necessariamente ser pessoas. A aula cita exemplos como:

* cliente do banco;
* sensor de distância;
* operadora de cartão de crédito.



Também podemos ter:

```text
Ator primário
    ↓
usa o sistema para atingir seu objetivo

Ator secundário
    ↓
auxilia o sistema ou outro ator
```

---

# 3. Caso de Uso

Cada funcionalidade é representada por uma **elipse dentro do sistema**.

Exemplo:

```text
        ( Verificar Saldo )
```

A recomendação da aula é começar o nome do caso de uso com um **verbo** e utilizar nomes simples e únicos. 

Por exemplo:

```text
✓ Verificar Saldo
✓ Realizar Pagamento
✓ Realizar Transferência
✓ Autenticar

evitar:

✗ Saldo
✗ Pagamento
✗ Transferência
```

A ideia é mostrar um **comportamento/objetivo**, não uma entidade.

---

# 4. Associação

É o relacionamento mais simples.

Uma linha entre um ator e um caso de uso significa:

> esse ator participa ou interage com esse caso de uso.

```text
Cliente
   |
   |
   +------ (Verificar Saldo)
```

Por exemplo:

```text
            (Verificar Saldo)
           /
Cliente --+
           \
            (Realizar Pagamento)
```

A aula define a associação justamente como a interação entre ator e caso de uso. 

---

# 5. `<<include>>`

Esse é um dos relacionamentos mais importantes.

`include` significa:

> para executar o caso de uso A, é **obrigatório executar B**.

Exemplo da aula:

```text
(Realizar Transferência)
          |
          | <<include>>
          v
(Verificar disponibilidade de saldo)
```

Toda vez que `Realizar Transferência` acontecer, `Verificar disponibilidade de saldo` também acontece.

O `include` é útil principalmente para:

* evitar repetição de comportamento;
* separar partes reutilizadas;
* decompor casos de uso mais complexos.



Imagine:

```text
Realizar Transferência
        \
         \ <<include>>
          \
      Verificar Saldo
          /
         / <<include>>
        /
Realizar Pagamento
```

Tanto pagamento quanto transferência precisam verificar saldo.

Em vez de escrever a mesma lógica nos dois casos, você separa:

```text
Verificar disponibilidade de saldo
```

## Direção da seta

Muito importante:

```text
CASO BASE ----<<include>>----> CASO INCLUÍDO
```

A seta vai **daquele que precisa do comportamento para o comportamento obrigatório**. 

---

# 6. `<<extend>>`

Aqui a lógica muda.

`extend` representa um comportamento que **pode acontecer**, mas não é obrigatório.

Na aula:

```text
(Instalar Token)
       |
       | <<extend>>
       v
(Autenticar)
```

Isso significa que durante `Autenticar`, em determinadas condições, pode ocorrer `Instalar Token`.

Por exemplo:

```text
se for primeiro acesso
       ↓
Instalar Token
```

Se não for o primeiro acesso:

```text
Autenticar
↓
continua normalmente
```

O slide diz que `extend` é útil para representar **fluxos alternativos complexos** ou variações de um caso de uso. 

## Direção da seta

Aqui costuma causar confusão:

```text
EXTENSOR ----<<extend>>----> BASE
```

Ou seja, a seta vai do comportamento opcional para aquele que está sendo estendido. 

---

# `include` vs `extend`

Essa diferença vale decorar pelo significado:

|                                 | `include`                                    | `extend`           |
| ------------------------------- | -------------------------------------------- | ------------------ |
| Execução                        | Obrigatória                                  | Opcional           |
| Objetivo                        | Reutilizar/decompor comportamento            | Adicionar variação |
| Caso base funciona sem o outro? | Não, aquele comportamento faz parte do fluxo | Sim                |
| Seta                            | Base → incluído                              | Extensor → base    |

O próprio exemplo da aula resume muito bem:

```text
Realizar Espirro
       |
       | <<include>>
       v
Fechar os Olhos
```

Fechar os olhos é tratado como **mandatório**.

Enquanto:

```text
Pedir Desculpas
       |
       | <<extend>>
       v
Realizar Espirro
```

Pedir desculpas é tratado como **opcional**. 

---

# 7. Generalização / Herança

A generalização serve para representar uma versão **mais específica** de algo geral.

Pode ser usada tanto entre:

* casos de uso;
* atores.

Exemplo dos casos de uso da aula:

```text
              (Realizar Pagamento)
                    △
                   / \
                  /   \
                 /     \
(Pagar Conta Corrente) (Pagar Poupança)
```

`Realizar Pagamento` é o comportamento mais geral.

Os dois abaixo representam formas específicas dele.

Para atores:

```text
        Cliente
           △
           |
    Cliente Select
```

Ou seja, `Cliente Select` é um tipo mais específico de `Cliente`.

A aula destaca que a herança ajuda a criar **variações mutuamente exclusivas** ou substituir significativamente partes do fluxo. 

---

### Para guardar

```text
RETÂNGULO     = sistema / assunto
BONECO        = ator
ELIPSE        = caso de uso
LINHA         = associação

<<include>>   = SEMPRE acontece
<<extend>>    = PODE acontecer
generalização = É UM TIPO DE
```

E a regra mais útil para montar um diagrama é pensar primeiro:

**Quem usa? → Para atingir qual objetivo? → Existe algum comportamento obrigatório, opcional ou especializado entre esses objetivos?**

---

## Casos de uso em métodos ágeis

**Histórias de usuário não substituem necessariamente casos de uso.** Eles possuem objetivos complementares.

As histórias representam necessidades menores, enquanto casos de uso podem reunir várias histórias relacionadas e oferecer uma **visão mais completa de um objetivo do usuário**. 

## Para lembrar

```text
Ator      = quem interage com o sistema
Caso de uso = objetivo/funcionalidade oferecida pelo sistema

include = obrigatório
extend  = opcional
herança = especialização

Caso de uso descreve O QUE acontece,
não COMO será programado.
```

Esses são os pontos centrais da aula e, principalmente, as diferenças entre **`include` e `extend`**, que tendem a ser uma das partes mais importantes para exercícios e provas.

# Concurrency, parallelism, and asynchronous I/O

## Begin with the bottleneck

Concurrency is a way to structure overlapping work. Parallelism is simultaneous execution. Neither guarantees speed.

Classify the workload first:

- **CPU-bound**: compression, parsing, simulation, image transforms. More useful cores/SIMD/GPU work may help.
- **I/O-bound**: waiting for network, disk, database, or user input. Overlap waits with other work.
- **contention-bound**: threads mostly wait on a shared lock/resource. More workers can make it worse.
- **latency-chain-bound**: sequential dependencies dominate; independent steps must be found before parallelism helps.

Amdahl's law gives a useful ceiling. If 20% of work is inherently serial, infinite parallel resources can improve total runtime by at most `1 / 0.20 = 5×`, before overhead.

## Blocking and non-blocking

A blocking read suspends the calling thread until data, EOF, an error, or interruption. That does not necessarily block the whole process; other threads may run.

Non-blocking/readiness-based code asks the OS which descriptors can make progress. A runtime event loop dispatches the relevant continuation. This scales well for many mostly-idle connections, but a CPU-heavy callback blocks that loop.

```text
event loop iteration
  ├─ receive ready events
  ├─ run short handler A
  ├─ advance handler B
  ├─ submit more I/O
  └─ wait for next events
```

Async I/O creates concurrency, not CPU parallelism. CPU-heavy work needs additional threads, processes, runtime workers, SIMD, or accelerators.

## Callbacks, futures, promises, and async/await

These are programming interfaces over deferred results.

- A **callback** is invoked when an operation makes progress or completes.
- A **future/promise** is a value representing a result that may arrive later.
- `async` commonly makes a function return such a value.
- `await` suspends the current coroutine until it is ready; a correctly designed runtime can execute other tasks meanwhile.

`await` is not the same as blocking an OS thread. It is also not automatically concurrent:

```python
# Sequential: second operation starts after the first finishes.
a = await fetch_a()
b = await fetch_b()

# Concurrent: both are started before waiting for both.
a, b = await asyncio.gather(fetch_a(), fetch_b())
```

Structured concurrency ties child-task lifetime to a lexical parent scope. It makes cancellation, error propagation, and cleanup easier than detached “fire-and-forget” tasks.

## Coroutines and runtime-scheduled tasks

A coroutine can suspend and later resume while retaining its logical execution state. Stackless coroutines usually compile suspension points into a state machine. Stackful fibers/green threads retain a logical call stack. Terminology varies by language, so inspect semantics rather than names.

Runtime scheduling maps many logical tasks onto fewer OS threads:

```text
10,000 logical tasks
        │ user-space scheduler
        ▼
  N carrier/OS threads
        │ kernel scheduler
        ▼
  M logical CPUs
```

This M:N model appears in goroutines, Erlang/BEAM processes, and Java virtual threads, with major semantic differences. Erlang actors communicate through mailboxes and isolate heaps conceptually; Go channels can carry pointers to shared objects; Java virtual threads retain normal Java shared-memory rules.

## Channels and actors do not abolish races by magic

Message passing reduces shared mutable state only if messages are immutable, copied, transferred, or ownership is disciplined. Sending a pointer through a channel can reintroduce a data race.

Actors add identity, a mailbox, sequential message handling per actor, and often supervision. They still face mailbox overload, message-order assumptions, distributed failure, and inconsistent multi-actor state.

## Runtime locks and current reality

The videos correctly connect CPython's traditional GIL with serialized Python bytecode while allowing blocking I/O and some native work to proceed concurrently. The detail is implementation-specific: current CPython also offers an optional free-threaded build, while the default build still uses the GIL. Ruby implementations, JVM languages, and alternative Python implementations have different constraints.

Likewise, “Java has no green threads” and “JavaScript has no parallelism” are historical snapshots. Modern Java has virtual threads scheduled by the JVM. Node.js supports worker threads for parallel JavaScript, while its built-in asynchronous I/O remains the usual choice for I/O-heavy work. Go goroutines have been asynchronously preemptible in supported configurations since Go 1.14; describing their scheduler as merely cooperative is outdated.

Implementation facts belong in versioned notes. The durable questions are:

1. What is the unit of concurrency?
2. Who schedules it: application, runtime, or kernel?
3. Can it run in parallel?
4. What state is shared?
5. What operation can block a carrier thread or event loop?
6. How are cancellation, errors, and backpressure propagated?

## Choosing a model

| Work | Good starting model |
|---|---|
| many network waits | async event loop or lightweight/virtual task per request |
| CPU-heavy independent items | bounded process/thread pool |
| mutable shared state | isolate ownership; otherwise explicit synchronization |
| durable slow task | external queue + idempotent workers |
| fault-contained component | process boundary or supervised actor, depending on failure needs |

Do not choose based on maximum connection-count anecdotes. Measure throughput, tail latency, memory per in-flight task, queueing delay, CPU utilization, and failure behavior under overload.

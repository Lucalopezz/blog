## Modelagem de Software

**Modelar um software** significa criar uma representação simplificada das características relevantes de um sistema dentro do domínio de um problema. Um mesmo sistema pode ser representado por **diferentes pontos de vista** e com diferentes níveis de formalismo. 

### Por que modelar?

A modelagem ajuda a pensar e validar decisões antes da implementação:

* Alterar um **modelo é mais barato** do que alterar código já implementado.
* Ajuda a identificar problemas de arquitetura antecipadamente.
* As decisões do modelo podem mudar durante a implementação.
* Quando o sistema muda, a modelagem também deve ser atualizada para continuar servindo como **documentação**. 

> **Ideia principal:** o modelo não precisa ser definitivo; ele serve para ajudar a pensar, comunicar e documentar decisões.

## UML — Unified Modeling Language

A **UML** é uma linguagem padronizada para representar e visualizar a arquitetura e outros aspectos de sistemas de software.

Ela permite comunicar decisões de projeto de maneira **independente da linguagem de programação**, facilitando a comunicação entre as pessoas envolvidas no projeto. 

Os diagramas UML são divididos principalmente em:

* **Estruturais** → representam a estrutura do sistema.
* **Comportamentais** → representam comportamentos e funcionalidades.
* **De interação** → representam a comunicação/interação entre elementos do sistema. 

Alguns exemplos mostrados no diagrama da página 7 são **Classes, Componentes, Objetos, Pacotes, Casos de Uso, Atividades, Máquina de Estados e Sequência**.

```

↓

```

## UML no desenvolvimento atual

Hoje o desenvolvimento possui requisitos que mudam rapidamente, ciclos de vida menores, software como serviço, cloud e métodos ágeis. Por isso, a UML não deve necessariamente significar criar uma documentação enorme antes de programar. 

A ideia apresentada na aula é usar UML de forma **pragmática**:

1. Criar diagramas para analisar alternativas.
2. Usá-los para discutir e entender o sistema.
3. Escolher uma solução.
4. Implementar.
5. Repetir quando necessário. 

Grady Booch e Ivar Jacobson destacam inclusive que, para grande parte dos projetos, aproximadamente **20% dos recursos da UML já atendem cerca de 80% das necessidades de modelagem**.  

## Resumo para lembrar

**Modelagem = abstrair o sistema antes/durante a implementação.**

**UML = linguagem padronizada para representar essa modelagem.**

O objetivo não é criar diagramas por obrigação, mas utilizá-los quando eles ajudam a **entender, discutir, decidir ou documentar algo que não fica claro apenas olhando o código**. A UML continua relevante quando usada dessa forma.

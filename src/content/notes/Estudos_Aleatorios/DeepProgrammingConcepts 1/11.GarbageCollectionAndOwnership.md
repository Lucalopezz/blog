# Garbage collection and ownership

## What automatic memory management promises

Garbage collection reclaims managed memory that is no longer reachable according to the runtime's model. It does not provide infinite memory, return pages to the OS immediately, close files promptly, prevent all leaks, or remove the need to understand allocation behavior.

A tracing collector views the heap as an object graph:

```text
roots: stacks, globals, runtime handles
        │
        ├──► A ──► B
        └──► C

unreachable: D ──► E       eligible for reclamation
```

If a cache, listener, global collection, or pending task still points to an object, that object is live from the collector's perspective even if the application no longer finds it useful. That is a logical memory leak.

## Reference counting

Reference counting increments/decrements an object's ownership count. When it reaches zero, destruction can be prompt and predictable.

Its central weakness is cycles:

```text
A ─► B
▲    │
└────┘
```

Neither count reaches zero after external references disappear. Systems address this with weak references, explicit cycle collectors, or ownership conventions. Atomic counter updates can also add multi-threading cost.

Python combines reference counting with a cyclic collector. Swift uses Automatic Reference Counting (ARC), which is compiler-inserted reference management rather than a tracing GC; developers break ownership cycles with `weak`/`unowned` references.

## Mark and sweep

A basic tracing collector:

1. starts from roots;
2. recursively marks reachable objects;
3. sweeps unmarked objects into reusable space.

Correctness becomes harder when the application mutates pointers while marking. Collectors use write/read barriers, snapshot algorithms, brief pauses, or combinations. “Concurrent GC” means some work overlaps application threads; it rarely means no pauses at all.

## Generational collection

Many applications exhibit the **generational hypothesis**: most new objects die young, while objects that survive several collections tend to survive longer. A collector can inspect a young generation frequently and old regions less often.

```text
allocate ─► young/eden ─survives─► survivor ─survives─► old
              │ collect often                    │ collect less often
              └─ most objects die here
```

References from old to young must be tracked, often with remembered sets/card tables, so a young collection need not scan the entire old generation. This bookkeeping uses memory and write barriers.

Generational is a workload hypothesis, not a universal superiority badge. Large objects, unusual lifetimes, and high mutation rates can reduce the benefit.

## Moving and compacting collectors

A moving collector copies or compacts live objects, improving locality and removing holes. References must be updated, so conservative pointers, native code, and pinned objects complicate movement.

Non-moving collectors avoid pointer rewriting/pinning problems but need other fragmentation strategies. Go's documented collector, for example, is tracing mark-sweep and non-moving. Modern JVMs offer multiple collectors with different region, pause, throughput, and compaction strategies; “the JVM GC” is not one algorithm.

## Stop-the-world, throughput, and latency

Collectors trade CPU, memory, throughput, and pause latency:

- collecting frequently keeps the heap smaller but consumes more CPU;
- collecting less often consumes more memory but may reduce GC CPU;
- concurrent work lowers pauses but competes with the application;
- compaction improves layout but requires movement and coordination.

Distinguish average throughput from tail latency. A service can process many requests per second yet violate its objective because rare GC pauses inflate p99/p999 response time.

The Go GC guide expresses the core trade-off clearly: more heap headroom generally allows fewer cycles and lower GC CPU, while a tighter target saves memory at higher collection cost.

## Deterministic resources are not garbage

File descriptors, database connections, locks, transactions, and sockets are limited external resources. Their release should be deterministic:

```python
with open("data.txt", "rb") as file:
    consume(file)
# descriptor is closed here even on an exception
```

Use RAII/destructors, `defer`, `using`, `try/finally`, or context managers as appropriate. Finalizers are nondeterministic fallbacks; a process may exit before they run.

## Ownership as an alternative/complement

C++ RAII and Rust ownership tie reclamation to lexical lifetimes without a tracing GC for ordinary values. Rust's borrow checker enforces aliasing/lifetime rules at compile time; `Rc`/`Arc`, interior mutability, arenas, and explicit cycles still require design choices.

There is no simple ladder where “manual is fastest, GC is slowest.” Region allocation, escape analysis, optimized collectors, cache locality, and programmer mistakes can reverse naive expectations. Compare whole-system outcomes: latency, memory, safety, development time, and operational predictability.

## Diagnose before tuning

Ask:

1. Is RSS growth caused by growing live data, retained heap, native allocation, mapped files, or fragmentation?
2. Is allocation rate high even if live heap is stable?
3. Which types/allocation sites dominate?
4. Are pauses actually harming tail latency?
5. Does the process approach a cgroup/container memory limit?

Use runtime-specific heap profiles, allocation flame graphs, GC logs/traces, and OS metrics together. Tuning heap sizes cannot fix an unbounded cache or `SELECT` that loads millions of rows.

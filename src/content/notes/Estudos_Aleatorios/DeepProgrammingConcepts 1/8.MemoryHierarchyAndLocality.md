# Memory hierarchy and locality

## “Memory” is a hierarchy

Programs experience storage layers with different capacity, latency, bandwidth, and persistence:

```text
fast, tiny, expensive/bit
registers
L1 cache
L2 cache
last-level cache (often L3)
DRAM
local SSD / persistent storage
remote storage
slow, huge, cheap/bit
```

Exact sizes and latencies depend on the processor. The durable idea is the gap: CPUs can execute much faster than DRAM can deliver scattered data. Caches try to keep needed data close enough that execution units do not starve.

Swap is not merely “slow RAM.” It is backing storage the OS may use for selected anonymous pages. Accessing an evicted page causes a fault and storage I/O, many orders of magnitude slower than a cache hit. See [[9.VirtualMemoryPagingAndSwap]].

## Cache lines and locality

CPUs generally move memory through caches in fixed-size cache lines, often 64 bytes. Reading one byte pulls its surrounding line. Performance depends heavily on:

- **spatial locality**: nearby addresses are used soon;
- **temporal locality**: recently used data is used again soon.

Compare two traversals of a row-major matrix:

```c
// Cache-friendly: consecutive addresses.
for (size_t row = 0; row < n; row++)
    for (size_t col = 0; col < n; col++)
        sum += matrix[row][col];

// Same arithmetic, poor locality for large matrices.
for (size_t col = 0; col < n; col++)
    for (size_t row = 0; row < n; row++)
        sum += matrix[row][col];
```

The second loop may be dramatically slower because it touches a new line/page on each iteration. Algorithmic Big-O is identical; memory behavior is not.

Arrays often outperform pointer-heavy linked structures for this reason. A linked list has cheap conceptual insertion, yet traversal can chase scattered pointers, miss caches, defeat prefetching, and increase allocation/GC work.

## Cache coherence is not thread synchronization

On a multicore CPU, hardware coherence tries to keep cores' views of cache lines consistent. It does not make multi-step operations atomic, establish the ordering your program needs, or prevent races. Language atomics and locks generate the required ordering operations.

Two threads can also hurt each other without logically sharing a variable. **False sharing** occurs when independent variables occupy one cache line:

```text
one cache line: [ counter_A | counter_B ]
core 0 writes A       core 1 writes B
          line ownership bounces between cores
```

Padding or reorganizing per-thread data can help after profiling. Blind padding wastes memory and can make locality worse elsewhere.

## TLB and pages

Virtual-to-physical translation uses page tables. CPUs cache recent translations in the Translation Lookaside Buffer (TLB). Random access across many pages can miss the TLB even if data fits in a higher-level cache.

Huge pages reduce the number of translations needed for large contiguous regions but increase allocation granularity, internal waste, and operational complexity. They are a measured optimization, not a default cure.

## NUMA

Large multiprocessor servers may have Non-Uniform Memory Access: a CPU accesses memory attached to its own NUMA node faster than remote-node memory. Thread migration and first-touch allocation can therefore change performance.

```bash
lscpu | sed -n '/NUMA/p'
numactl --hardware             # if installed
```

NUMA helps explain why “all RAM is equivalent” fails on larger servers, and why worker affinity and allocator arenas sometimes matter.

## Bandwidth, latency, and pipelines

Latency is time until one access completes; bandwidth is data transferred per unit time. Sequential streaming may use bandwidth efficiently even with nontrivial latency. Pointer chasing makes each address depend on the previous load, exposing latency.

Similarly, GHz alone does not predict performance. Instruction-level parallelism, branch prediction, vector instructions, cache behavior, and memory stalls decide how much useful work completes per cycle.

## Practical measurement

```bash
perf stat -e cycles,instructions,cache-references,cache-misses ./program
perf record -g ./program
perf report
```

On managed runtimes, combine OS counters with runtime allocation/GC profilers. A cache miss is not automatically a bug; look for high-cost code where a layout or traversal change is semantically reasonable.

Useful design habits:

- process data in batches that fit useful cache levels;
- prefer contiguous representations for hot traversal;
- avoid allocating an object per tiny item without need;
- partition mutable data by ownership to reduce coherence traffic;
- benchmark realistic data sizes, not toy inputs that fit entirely in cache.

The allocator in [[10.HeapAllocationAndFragmentation]] and GC in [[11.GarbageCollectionAndOwnership]] operate on top of these physical constraints.

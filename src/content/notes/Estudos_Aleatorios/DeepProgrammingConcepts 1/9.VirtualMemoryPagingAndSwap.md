# Virtual memory, paging, and swap

## The illusion

Each process sees a private virtual address space. Virtual addresses are divided into pages; page tables map virtual page numbers to physical frames or mark them absent. The CPU's memory-management unit performs translation, assisted by the TLB.

```text
process virtual address
   │ virtual page + offset
   ▼
TLB ─miss─► page-table walk
   │ mapped physical frame + same offset
   ▼
cache / DRAM
```

The page-table entry also carries protection and status bits. A user write to a read-only page raises a fault. The kernel inspects the reason and either resolves it—perhaps COW—or delivers an error such as `SIGSEGV`.

## Mappings and demand paging

A virtual region can be:

- anonymous memory backing stacks/heaps;
- file-backed executable or shared-library pages;
- a memory-mapped data file;
- shared memory;
- reserved but not yet physically committed;
- inaccessible guard pages.

Mapping a large range does not mean every byte occupies RAM. Physical frames are commonly assigned on first access. Executable pages can be demand-loaded from files and discarded/reloaded later because the file remains their backing store.

This is why memory metrics differ:

- **VSS/VSZ**: total virtual mappings; includes untouched reservations and shared mappings.
- **RSS**: pages currently resident in RAM, but may count shared pages in each process.
- **PSS**: resident shared pages divided proportionally among mapping processes.
- **private dirty/anonymous**: often closer to memory that would actually disappear when the process exits.

Never infer “this program uses 2 GB of RAM” from VSZ alone.

```bash
cat /proc/<pid>/maps
cat /proc/<pid>/smaps_rollup
pmap -x <pid>
```

## Copy-on-write

After `fork`, parent and child can share physical pages marked read-only/COW. A write fault makes the kernel copy only the changed page. This makes process creation and preloading strategies efficient when most pages remain unchanged.

COW savings can evaporate when a runtime writes to many pages after forking—through JIT compilation, GC metadata, reference counters, or ordinary mutation. “Fork is cheap” describes an initial mapping strategy, not the full lifetime cost.

## Page faults

- A **minor fault** can be resolved without reading from persistent storage, such as allocating a zero page or establishing an already-cached file mapping.
- A **major fault** requires storage I/O and is much more expensive.

Page faults are normal. A rising major-fault rate with high storage latency and low progress indicates memory pressure or an access pattern that defeats the working set.

```bash
/usr/bin/time -v ./program
pidstat -r -p <pid> 1
vmstat 1
```

## Swap and memory pressure

Swap gives the kernel a place to evict anonymous pages. It can preserve RAM for actively used pages and filesystem cache. Occasional swap use is not automatically bad; repeated eviction and refaulting of the active working set is **thrashing**.

When memory cannot be reclaimed fast enough, Linux allocation can fail and the OOM killer may select a process. The selection is policy-driven; it is not simply “the oldest app.” Mobile systems layer additional lifecycle policies and pressure handlers above their kernels.

Inside containers, a cgroup memory limit can trigger a cgroup-local OOM even when the host has free RAM. This is a frequent source of “but the server still had memory” confusion.

## 32-bit and 64-bit

An N-bit address could theoretically distinguish `2^N` byte addresses. Real CPUs implement fewer virtual/physical address bits, and OSes reserve parts of the address space. The exact limits are architecture- and generation-specific.

For a 32-bit process, roughly 4 GiB of virtual address values exist, often split between user and kernel ranges. Fragmentation could prevent one large contiguous mapping even when the sum of holes was large enough. A 64-bit address space makes address-space exhaustion far less common, but does not provide unlimited physical RAM.

Also, 64 bits is not “the square of 32 bits.” The **number of representable bit patterns** grows from `2^32` to `2^64`, which is `2^32` times as many patterns.

## Stack versus heap mappings

Each thread receives a stack region, often mostly reserved virtual space with guard pages and on-demand commitment. Function call frames, return addresses, saved registers, and many local variables live there. Machine instructions live in executable mappings, not “on the stack.”

Deep recursion or unusually large stack allocations can hit a guard page and cause stack overflow. Dynamic objects whose lifetime/size cannot be handled conveniently in a call frame use heap allocation; compiler escape analysis may choose between them.

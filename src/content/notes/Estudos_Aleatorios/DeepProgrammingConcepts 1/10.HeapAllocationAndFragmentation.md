# Heap allocation and fragmentation

## Layers of allocation

“The heap” can mean different layers:

```text
application objects
    ▼
language runtime / GC heap (if present)
    ▼
native allocator: malloc, jemalloc, tcmalloc, mimalloc...
    ▼
virtual mappings obtained from the OS
    ▼
physical pages assigned on demand
```

A `malloc(24)` call normally does not ask the kernel for 24 bytes. The allocator obtains larger regions, maintains metadata and free lists, and returns a suitably aligned block. This amortizes syscall/mapping cost.

`free(ptr)` marks the block reusable by the allocator. It does not guarantee immediate return to the OS, a lower RSS, or zeroing. Returning scattered pages may be impossible or counterproductive; allocators often retain them for future requests.

## Why allocation is difficult

An allocator balances:

- fast allocation/deallocation;
- low memory overhead;
- low fragmentation;
- scalability under many threads;
- locality and cache behavior;
- prompt return of unused pages;
- debugging/hardening against misuse.

No allocator wins every workload. Claims such as “replace glibc's allocator with X and everything improves” require workload-specific measurement and compatibility testing.

## External and internal fragmentation

**External fragmentation**: enough free bytes exist in total, but not in a suitable contiguous region.

```text
used  free  used  free  used
[AA]  [..]  [BB]  [..]  [CC]

two free units exist, but no two-unit contiguous block
```

**Internal fragmentation**: the allocator gives a block larger than requested due to alignment or size classes. A 33-byte request served from a 48-byte class wastes 15 bytes inside the allocated block.

Modern virtual memory changes the physical meaning of “contiguous”: a contiguous **virtual** range may map to noncontiguous physical frames. Allocators chiefly manage contiguous virtual ranges and page-sized interactions with the OS.

## Size classes, bins, spans, and arenas

Grouping requests into size classes makes lookup and reuse fast and limits some fragmentation. Exact terms vary:

- a **bin/free list** groups reusable blocks of similar size;
- a **span/slab/run** manages one or more pages split into similar objects;
- an **arena** is a larger allocation domain, often used to reduce lock contention;
- a **thread cache** keeps small blocks close to a thread.

Per-thread caches and multiple arenas improve throughput but may strand free memory where another thread or arena cannot immediately reuse it. Thus lower contention can cost a larger footprint. Thread count and allocation migration matter.

The video names ptmalloc, tcmalloc, and jemalloc to illustrate this trade-off. Treat its sizes, arena counts, speed ratios, and default-language allocator claims as implementation/version snapshots, not invariants. Rust, for example, uses the platform's configured global allocator by default in current toolchains; jemalloc can be selected but is not an intrinsic reason Rust is memory-efficient.

## Stack allocation is different

A call stack usually adjusts a pointer to reserve a frame and reverses that adjustment on return: extremely cheap and naturally lifetime-scoped. Heap allocation supports values with dynamic size or lifetime beyond one call, but requires tracking/reclamation.

Compilers may use escape analysis:

```go
func value() int {
    x := 42        // can usually remain in a stack frame/register
    return x
}

func pointer() *int {
    x := 42
    return &x      // x must outlive the call; may escape to heap
}
```

The language semantics do not always promise the physical location; optimization decides.

## Memory bugs in manual management

- **leak**: allocated memory is never made reusable after it is no longer needed;
- **use-after-free**: code accesses a block after its lifetime ended;
- **double free**: the same ownership is released twice;
- **buffer overflow/underflow**: access crosses allocation boundaries;
- **invalid free**: pointer did not designate the required allocation start;
- **uninitialized read**: code observes data never given a valid value.

These can silently corrupt allocator metadata and fail much later than the original bug.

Useful tools:

```bash
# Rebuild a native program with debug info and sanitizers when supported.
cc -g -O1 -fsanitize=address,undefined program.c -o program
./program

valgrind --leak-check=full ./program    # slower; if installed
```

## Why RSS may stay high after freeing

Several explanations are possible:

1. blocks are free inside the allocator but share pages with live blocks;
2. a thread cache or arena retains reusable pages;
3. the runtime heap retains space to avoid reacquiring it;
4. allocator metadata or fragmentation consumes it;
5. the kernel still counts pages until reclaim/advice occurs;
6. live references really remain.

This distinction matters: retained reusable memory is not the same as an unreachable leak, though both can violate a container limit.

## Allocation-aware application design

Most wins happen above allocator tuning:

- stream a large file/query instead of loading all rows;
- enforce request/body/result limits before allocation;
- reuse bounded buffers where ownership is clear;
- batch tiny objects in a contiguous representation;
- cap queues and concurrent tasks;
- remove accidental object churn from hot loops;
- profile allocation rate and peak live data.

# 4.Redis

Resumo de **Banco de Dados NoSQL - Redis** (`BD2_16_NoSQL_Redis.pdf`), da professora Silvana Maria Affonso de Lara, com material adaptado de Fábio Octaviano / Silvana Lara. Os exemplos do resumo vêm da aula; o exercício final está separado de sua resolução. O tutorial de Docker fica na última parte.

## 1. O que é Redis?

**Redis (Remote Dictionary Server)** é um banco de dados **NoSQL, em memória e orientado a chave-valor**. A chave identifica o dado; o valor pode ser uma string ou uma estrutura, como lista, conjunto ou hash.

Por trabalhar com os dados na **RAM**, permite leituras e escritas rápidas. Na aula, aparece como solução para cache, sessões web, contadores, filas, rankings e comunicação em tempo real. Também oferece persistência em disco, comandos atômicos, transações e recursos de replicação e distribuição dos dados.

| Estrutura estudada | Ideia principal | Exemplo da aula |
| --- | --- | --- |
| String | Um valor associado a uma chave | Nome, sessão e contador de acessos |
| Bitmap | Bits para marcar 0 ou 1 | Faltas de alunos |
| List | Sequência de strings, com posições | Últimas notícias e fila de e-mails |
| Set | Membros únicos, sem ordem | Relacionamentos de uma rede social |
| Sorted set / ZSET | Membros únicos ordenados por pontuação | Ranking de jogadores |
| Hash | Campos e valores dentro de uma chave | Dados de uma disciplina ou jogador |
| HyperLogLog | Estimativa da quantidade de elementos distintos | IPs únicos de visitantes |

> [!tip] Onde digitar os comandos
> Os comandos Redis desta nota são executados no **`redis-cli`**, o shell do Redis. Digite cada comando em uma única linha, mesmo quando a tela mostrar uma quebra visual. Os comandos `docker ...` vão no terminal do computador; o passo a passo para abrir o shell está no final.

## 2. Chaves, valores e padrões de nomes

### Criar, consultar, atualizar e remover

```text
SET nome "Joana"
GET nome
SET "nome completo" "Joana da Silva"
GET "nome completo"
SET "nome completo" "Maria Joana da Silva"
DEL "nome completo"
KEYS *
```

- `SET` cria ou substitui o valor.
- `GET` recupera o valor de uma string; se a chave não existir, retorna `(nil)`.
- `DEL` remove a chave e seu valor.
- `KEYS *` lista as chaves existentes.
- Nomes de chaves diferenciam maiúsculas e minúsculas. Aspas permitem usar espaços.

A aula também apresenta `FLUSHALL`, que **apaga todas as chaves de todos os bancos da instância**. É um comando de limpeza, não uma etapa para executar antes de cada exemplo.

### Padronizar nomes e gravar vários valores

Os dois-pontos ajudam a organizar o significado das chaves:

```text
SET "ano:semestre:curso:disciplina" "2025:1:ADS:BDD2"
SET "ano:semestre:curso:disciplina:professor" "2025:1:ADS:BDD2:Silvana"
SET "professor:curso:ano:disciplina:total_aprovados" "Silvana:ADS:2025:BDD2:18"
```

Para definir vários pares chave-valor em um comando, use `MSET`:

```text
MSET "ADS:2025:1:BDD2:alunos" "André Barreto, Beatriz Silva, Julia Souza" "ADS:2025:1:APR1:alunos" "Felipe Castro, Laura Cardoso, Pedro Matos"
MSET "ADS:2025:1:BDD2:professores" "Silvana Lara, Fábio Octaviano" "ADS:2025:1:APR1:professores" "Silvana Lara, Eloize Seno" "ADS:2025:1:BDD1:professores" "Fábio Octaviano, Pablo Castro"
```

### Pesquisar chaves

```text
KEYS "ADS:2025*"
KEYS "ADS:2025:1:BDD2*"
KEYS "ADS:2025:1:*:professores"
KEYS "ADS:2025:1:BDD?:professores"
KEYS "ADS:2025:?:BDD[12]:professores"
```

`*` aceita uma sequência de caracteres; `?`, um único caractere; `[12]`, uma das opções indicadas. Esses padrões procuram **nomes de chaves**, não o conteúdo dos valores.

## 3. Sessões web e expiração

Quando um site usa mais de um servidor web, armazenar as sessões no Redis permite que os servidores consultem os mesmos dados do usuário. A expiração limita por quanto tempo a sessão existe.

Exemplo da aula:

```text
SET "sessao:usuario:1001" "foctaviano@ifsp.edu.br"
EXPIRE "sessao:usuario:1001" 1800
TTL "sessao:usuario:1001"
GET "sessao:usuario:1001"
```

`EXPIRE` define o prazo em **segundos**: 1.800 segundos são 30 minutos. `TTL` consulta quanto tempo falta. Depois da expiração, `GET` retorna `(nil)`.

A aplicação pode executar novamente `EXPIRE` a cada requisição do usuário para renovar o prazo. Essa renovação depende da aplicação; consultar a chave não renova a sessão automaticamente.

## 4. Contadores e atomicidade

Para contar acessos à página de contato, a aula começa com:

```text
SET ifsp:/contato:01-05-2025 1
SET ifsp:/contato:01-05-2025 2
```

Fazer `GET`, somar na aplicação e depois `SET` abre espaço para dois clientes lerem o mesmo valor e um sobrescrever a atualização do outro. `INCR` reúne a operação em um **comando atômico**:

```text
INCR ifsp:/contato:01-05-2025
DECR ifsp:/contato:01-05-2025
```

Na sequência acima, o contador vai de 2 para 3 e depois volta a 2. A atomicidade vale para cada comando; ela não transforma comandos separados em uma única operação.

Para variar a quantidade, use `INCRBY` e `DECRBY`. No exemplo de compras, partindo de uma chave inexistente:

```text
INCRBY compras:01-05-2025:quantidade 15
INCRBY compras:01-05-2025:quantidade 17
INCRBY compras:01-05-2025:quantidade 2
DECRBY compras:01-05-2025:quantidade 2
INCRBYFLOAT compras:01-05-2025:quantidade 10.50
INCRBYFLOAT compras:01-05-2025:quantidade -0.50
```

Os resultados sucessivos são **15, 32, 34, 32, 42.5 e 42**. Para diminuir um valor decimal, passa-se um número negativo a `INCRBYFLOAT`. Esses valores são manipulados como números pelos comandos, mas a chave continua sendo do tipo **string**.

## 5. Bits: registrar faltas dos alunos

Na aula, **1 significa falta** e **0 significa ausência de falta registrada**. O ID do aluno é usado como posição do bit: 11 para André Barreto, 23 para Beatriz Silva e 35 para Julia Souza.

```text
SETBIT "ADS:2025:1:BDD2:01-05-2025" 11 1
SETBIT "ADS:2025:1:BDD2:01-05-2025" 23 1
SETBIT "ADS:2025:1:BDD2:01-05-2025" 35 1
BITCOUNT "ADS:2025:1:BDD2:01-05-2025"
```

`BITCOUNT` retorna **3**, pois há três bits marcados como 1. Posições ainda não marcadas são lidas como 0.

Registrando os outros dias:

```text
SETBIT "ADS:2025:1:BDD2:02-05-2025" 11 1
SETBIT "ADS:2025:1:BDD2:02-05-2025" 35 1
SETBIT "ADS:2025:1:BDD2:05-05-2025" 11 1
SETBIT "ADS:2025:1:BDD2:05-05-2025" 23 1
```

| Aluno | 01/05 | 02/05 | 05/05 | AND: faltou todos os dias | OR: faltou em algum dia |
| --- | --- | --- | --- | --- | --- |
| 11 | 1 | 1 | 1 | 1 | 1 |
| 23 | 1 | 0 | 1 | 0 | 1 |
| 35 | 1 | 1 | 0 | 0 | 1 |

`BITOP` grava o resultado em uma chave de destino:

```text
BITOP AND "FALTAS:ADS:2025:1:BDD2:01-e-02-e-05-05-2025" "ADS:2025:1:BDD2:01-05-2025" "ADS:2025:1:BDD2:02-05-2025" "ADS:2025:1:BDD2:05-05-2025"
BITCOUNT "FALTAS:ADS:2025:1:BDD2:01-e-02-e-05-05-2025"
BITOP OR "ALGUMAFALTA:ADS:2025:1:BDD2:01-ou-02-ou-05-05-2025" "ADS:2025:1:BDD2:01-05-2025" "ADS:2025:1:BDD2:02-05-2025" "ADS:2025:1:BDD2:05-05-2025"
BITCOUNT "ALGUMAFALTA:ADS:2025:1:BDD2:01-ou-02-ou-05-05-2025"
```

As contagens são **1** para AND e **3** para OR. O retorno do próprio `BITOP` é o **tamanho do resultado em bytes**, não a quantidade de alunos.

## 6. Listas: notícias e fila de e-mails

### Notícias mais recentes primeiro

`LPUSH` insere à esquerda, na posição 0. Assim, a notícia inserida por último aparece primeiro:

```text
LPUSH ultimas_noticias "Duas praias brasileiras são eleitas entre as 50 melhores do mundo"
LPUSH ultimas_noticias "Peixe gigante da Amazônia invade rios de São Paulo"
LPUSH ultimas_noticias "O corpo alerta: 11 sinais de que você está muito estressado"
LPUSH ultimas_noticias "'Haverá sinais': estes são os indícios de que você está caindo em um golpe"
LINDEX ultimas_noticias 0
LLEN ultimas_noticias
LRANGE ultimas_noticias 1 2
LRANGE ultimas_noticias 0 -1
LTRIM ultimas_noticias 0 2
LRANGE ultimas_noticias 0 -1
```

- `LINDEX` consulta uma posição; `LLEN` retorna o tamanho.
- `LRANGE` consulta um intervalo com **as duas extremidades incluídas**. `0 -1` significa do primeiro ao último elemento.
- `LTRIM 0 2` mantém apenas as três notícias mais recentes e remove as demais da lista.

### Fila de confirmação de e-mails

Para atender na ordem de chegada, insira à direita com `RPUSH` e retire à esquerda com `LPOP`:

```text
RPUSH "fila:confirma-email" "silaffonso@ifsp.edu.br"
RPUSH "fila:confirma-email" "professor@ifsp.edu.br"
RPUSH "fila:confirma-email" "aluno@ifsp.edu.br"
LLEN "fila:confirma-email"
LINDEX "fila:confirma-email" 0
LRANGE "fila:confirma-email" 0 2
LINSERT "fila:confirma-email" BEFORE "professor@ifsp.edu.br" "fabio@gmail.com"
LINSERT "fila:confirma-email" AFTER "fabio@gmail.com" "silvana@yahoo.com"
LPOP "fila:confirma-email"
RPOP "fila:confirma-email"
```

`LINSERT` insere antes ou depois de um **valor já presente**. `LPOP` e `RPOP` retornam e removem um elemento, respectivamente do início e do fim.

A aula também mostra retirar até três elementos de uma vez:

```text
LPOP "fila:confirma-email" 3
```

### Esperar por uma tarefa sem busy wait

Chamar `LPOP` repetidamente enquanto a fila está vazia gera espera ocupada (*busy wait*). Com `BLPOP`, o cliente espera por um elemento:

```text
BLPOP "fila:confirma-email" 30
```

Se houver um elemento, ele é removido e retornado imediatamente. Se não houver, o cliente espera até **30 segundos**; se nada chegar, recebe `(nil)`. O retorno com sucesso contém o nome da lista e o elemento retirado.

```text
BLPOP "fila:confirma-email" 0
```

O tempo **0** significa esperar indefinidamente. Outro cliente pode inserir um e-mail com `RPUSH` para liberar essa espera.

## 7. Conjuntos: relacionamentos

Um **set** guarda strings sem repetição e sem garantir ordem. O exemplo de comandos da aula usa Carlos e Daniel:

```text
SADD "relacionamentos:Carlos" "Paulo" "Lucia" "Julio"
SADD "relacionamentos:Carlos" "Paulo"
SMEMBERS "relacionamentos:Carlos"
SCARD "relacionamentos:Carlos"
SREM "relacionamentos:Carlos" "Paulo"
SISMEMBER "relacionamentos:Carlos" "Julio"
SISMEMBER "relacionamentos:Carlos" "Joana"
SADD "relacionamentos:Daniel" "Ana" "Lucia" "Leonardo"
```

O primeiro `SADD` retorna **3**; repetir Paulo retorna **0**, pois não acrescenta um membro novo. `SCARD`, antes da remoção, retorna **3**. `SISMEMBER` retorna **1** para Julio e **0** para Joana.

Depois de remover Paulo, as operações entre os conjuntos ficam:

```text
SINTER "relacionamentos:Carlos" "relacionamentos:Daniel"
SUNION "relacionamentos:Carlos" "relacionamentos:Daniel"
SDIFF "relacionamentos:Carlos" "relacionamentos:Daniel"
SMOVE "relacionamentos:Daniel" "relacionamentos:Daniel:excluidos" "Leonardo"
```

- `SINTER`: interseção, retorna **Lucia**, amiga em comum.
- `SUNION`: união, retorna **Lucia, Julio, Ana e Leonardo**, sem repetição e sem ordem garantida.
- `SDIFF`: membros de Carlos que não estão em Daniel; retorna **Julio**. A ordem dos conjuntos no comando importa.
- `SMOVE`: move **Leonardo** do conjunto de Daniel para o conjunto de excluídos.

## 8. Conjuntos ordenados: ranking de jogadores

Um **sorted set** associa cada membro a uma pontuação (*score*) e ordena por ela:

```text
ZADD pontuacoes 85378.5 Carlos
ZADD pontuacoes 103853 Joana
ZADD pontuacoes 33786 Lucia
ZADD pontuacoes 8754 Paulo
TYPE pontuacoes
ZCARD pontuacoes
ZRANGE pontuacoes 0 -1
ZREVRANGE pontuacoes 0 -1
ZREVRANGE pontuacoes 0 1
ZREVRANGE pontuacoes 0 -1 WITHSCORES
```

`TYPE` retorna **zset**, e `ZCARD`, **4**. `ZRANGE` lista em ordem crescente de pontuação; `ZREVRANGE`, em ordem decrescente. O intervalo `0 1` retorna os **dois** primeiros: Joana e Carlos. `WITHSCORES` inclui as pontuações.

Para consultar um jogador e alterar pontos:

```text
ZSCORE pontuacoes Lucia
ZRANK pontuacoes Lucia
ZREVRANK pontuacoes Lucia
ZINCRBY pontuacoes 50000 Paulo
ZINCRBY pontuacoes -2000 Paulo
ZCOUNT pontuacoes 40000 90000
```

Lucia tem **33.786 pontos**. Antes das alterações, `ZRANK` retorna **1** (segunda menor pontuação) e `ZREVRANK` retorna **2** (terceira maior). **Os índices começam em 0.**

Paulo passa de 8.754 para 58.754 e depois para **56.754**. Nesse estado, `ZCOUNT` retorna **2**: Carlos e Paulo estão entre 40.000 e 90.000 pontos, incluindo os limites. Para apagar todo o ranking, a aula usa `DEL pontuacoes`.

## 9. Hashes: vários campos na mesma chave

Em vez de uma chave separada para cada informação, um **hash** agrupa pares **campo-valor**:

```text
HSET "2025:1:ADS:BDD2" "professores" "Silvana Lara, Fabio Octaviano"
HSET "2025:1:ADS:BDD2" "total_alunos" 23
HSET "2025:1:ADS:BDD2" "total_aprovados" 18
HGET "2025:1:ADS:BDD2" "professores"
HDEL "2025:1:ADS:BDD2" "total_aprovados"
HMSET "2025:1:ADS:APR1" "professores" "Silvana Lara, Eloize Seno" "total_alunos" 20 "total_aprovados" 14
HGET "2025:1:ADS:APR1" "professores"
HGETALL "2025:1:ADS:APR1"
```

`HSET` define um campo; `HGET` consulta um campo; `HDEL` remove um campo. A aula usa `HMSET` para gravar vários campos de uma vez. `HGETALL` retorna **os campos e seus valores**, não apenas os valores.

### Dados dos jogadores

Este é outro exemplo da aula, independente do ZSET anterior:

```text
HSET "jogador:1" "nome" "Carlos"
HSET "jogador:1" "pontos" 85348
HSET "jogador:2" "nome" "Joana"
HSET "jogador:2" "pontos" 103853
HINCRBY "jogador:1" "pontos" 10
HINCRBYFLOAT "jogador:1" "pontos" 20.5
HEXISTS "jogador:1" "senha"
HEXISTS "jogador:1" "pontos"
HKEYS "jogador:1"
HVALS "jogador:1"
```

Carlos passa a ter **85.378,5 pontos** nesse hash. `HEXISTS` retorna **0** para senha e **1** para pontos. `HKEYS` lista os campos; `HVALS`, os valores. Alterar o hash não atualiza automaticamente o conjunto `pontuacoes`.

### Sessão com mais de uma informação

```text
HMSET "sessao:usuario:1309" "nome" "silvana" "sobrenome" "lara" "total_de_produtos" "3"
EXPIRE "sessao:usuario:1309" 1800
TTL "sessao:usuario:1309"
HGET "sessao:usuario:1309" "nome"
```

A expiração é aplicada à **chave da sessão inteira**. Depois dos 30 minutos, o `HGET` retorna `(nil)`.

## 10. HyperLogLog: estimar visitantes distintos

**HyperLogLog** estima a cardinalidade, isto é, quantos elementos distintos existem. Usa pouco espaço para contagens grandes, mas **não permite listar os elementos** como `SMEMBERS` faz em um set.

O exemplo da aula reúne os IPs de três páginas:

```text
PFADD site:pagina1 "10.1.1.1" "20.2.2.2" "30.3.3.3" "40.4.4.4" "50.5.5.5" "10.1.1.1" "60.6.6.6"
PFADD site:pagina2 "70.7.7.7" "80.8.8.8" "30.3.3.3" "40.4.4.4" "50.5.5.5"
PFADD site:pagina3 "10.1.1.1" "20.2.2.2" "30.3.3.3" "90.9.9.9" "30.3.3.3"
PFCOUNT site:pagina1
PFCOUNT site:pagina2
PFCOUNT site:pagina3
PFCOUNT site:pagina1 site:pagina2 site:pagina3
PFMERGE site:paginas site:pagina1 site:pagina2 site:pagina3
PFCOUNT site:paginas
```

| Medida nos dados da aula | Quantidade |
| --- | --- |
| Visitas totais, contando repetições | 17 |
| IPs distintos na página 1 | 6 |
| IPs distintos na página 2 | 5 |
| IPs distintos na página 3 | 4 |
| Soma dos distintos por página | 15 |
| IPs distintos no site inteiro | 9 |

Somar 6 + 5 + 4 conta novamente os IPs que visitaram mais de uma página. `PFCOUNT` com várias chaves estima os distintos da **união**. `PFMERGE` grava essa união em outro HyperLogLog. Para esses dados, a contagem retornada é **9**; a estrutura continua sendo probabilística.

## 11. Transações: MULTI, EXEC e WATCH

`MULTI` inicia o enfileiramento dos comandos. Eles ficam aguardando até `EXEC`, que os executa em sequência, sem comandos de outros clientes intercalados durante essa execução.

Na transferência da aula, o usuário 1 começa com 100 e o usuário 2 com 50. A preparação desses saldos e a transferência de 30 ficam:

```text
SET user:1:saldo 100
SET user:2:saldo 50
GET user:1:saldo
GET user:2:saldo
MULTI
DECRBY user:1:saldo 30
INCRBY user:2:saldo 30
EXEC
```

O resultado é **70** para o usuário 1 e **80** para o usuário 2. Os comandos dentro de `MULTI` respondem `QUEUED` antes do `EXEC`. Como mostrado na aula, um erro de sintaxe detectado no enfileiramento impede a execução da transação.

### Evitar uma transferência baseada em saldo alterado

```text
WATCH user:1:saldo
GET user:1:saldo
MULTI
DECRBY user:1:saldo 30
INCRBY user:2:saldo 30
EXEC
```

`WATCH` monitora a chave **antes da leitura**. Se outro cliente alterar `user:1:saldo` entre `WATCH` e `EXEC`, a transação não é executada e `EXEC` retorna `(nil)`. A aplicação precisa reler o saldo e decidir se tenta novamente. Sem alteração concorrente, a transferência é executada sobre os saldos atuais.

## 12. Canais: publicação e assinatura

No modelo **Pub/Sub**, clientes assinam canais e recebem as mensagens publicadas neles. O exemplo da aula usa os canais da empresa `geral`, `dev` e `teste`.

Em um shell, faça a assinatura:

```text
SUBSCRIBE geral dev teste
```

Em **outro shell conectado ao mesmo Redis**, publique:

```text
PUBLISH geral "Reuniao presencial amanha"
```

O shell assinante exibe a mensagem recebida. A aula também apresenta `UNSUBSCRIBE teste` para desfazer a assinatura do canal `teste`.

No `redis-cli` interativo, o modo de assinatura fica escutando mensagens. Para sair desse modo durante o estudo, use **Ctrl+C** e abra o shell novamente para os próximos comandos.

## 13. Persistência: AOF e RDB

O Redis trabalha em memória. Para recuperar dados após um desligamento, é preciso que eles tenham sido persistidos em disco. A aula apresenta duas formas:

- **AOF (Append Only File):** registra operações de escrita para reconstruir os dados.
- **RDB:** salva snapshots, isto é, retratos do conjunto de dados em determinados momentos.

Na instalação local usada nos slides, o AOF é habilitado em `/etc/redis/redis.conf`:

```text
appendonly yes
appendfsync everysec
```

`appendfsync everysec` sincroniza as escritas em disco a cada segundo. É a configuração de equilíbrio entre desempenho e segurança apresentada na aula.

Os exemplos de regras para snapshots RDB são:

```text
save 900 1
save 300 10
save 60 10000
```

Isso configura snapshots quando houver, respectivamente, ao menos **1 alteração em 900 segundos**, **10 em 300 segundos** ou **10.000 em 60 segundos**.

O teste da aula grava `SET cidade "São Carlos"`, reinicia o Redis e consulta `GET cidade`. Os arquivos apresentados incluem `dump.rdb` e arquivos de AOF, que podem estar em um diretório `appendonlydir`.

No cenário de cache, a aula recomenda manter a origem das informações em outro banco e guardar no Redis os dados processados para acelerar consultas. No Docker, a configuração de persistência e esse mesmo teste aparecem no tutorial final.

## 15. Respostas do exercício da Stream+

Esta é uma **proposta de resolução**, pois o PDF não traz gabarito nem uma base de usuários e conteúdos. Os identificadores `filme:1`, `serie:1` e `documentario:1`, os gêneros e as tags abaixo são dados mínimos escolhidos para executar o exercício. Carlos é o nome reutilizado do exemplo de jogadores da aula. As estruturas e os comandos usados foram todos apresentados nos slides.

Os exemplos desta parte usam o prefixo `stream:` e devem ser executados na ordem, uma vez, para obter os resultados descritos.

### 1. Cadastro de usuários: hash

Um usuário possui vários campos. Assim como a aula agrupa nome e pontos em `jogador:1`, podemos agrupar os dados do usuário:

```text
HSET "stream:usuario:1" "nome" "Carlos"
HGET "stream:usuario:1" "nome"
HGETALL "stream:usuario:1"
```

A chave identifica o usuário; `nome` é um campo. Outros dados do cadastro podem ser adicionados com `HSET`, sem criar uma chave separada para cada campo.

### 2. Histórico de visualizações: lista

A lista preserva a sequência das visualizações. Usando a lógica das últimas notícias, `LPUSH` coloca a visualização mais recente primeiro:

```text
LPUSH "stream:usuario:1:historico" "filme:1"
LPUSH "stream:usuario:1:historico" "serie:1"
LPUSH "stream:usuario:1:historico" "filme:1"
LRANGE "stream:usuario:1:historico" 0 -1
LINDEX "stream:usuario:1:historico" 0
LLEN "stream:usuario:1:historico"
```

O histórico fica **filme:1, serie:1, filme:1**, do mais recente para o mais antigo. A repetição é permitida: o usuário pode assistir ao mesmo conteúdo novamente. `LLEN` retorna **3**. A lista registra a ordem; o enunciado não exige guardar datas.

### 3. Conteúdos mais assistidos: sorted set

Cada conteúdo é um membro, e seu score é o número de visualizações. Para as três visualizações do item anterior:

```text
ZINCRBY "stream:ranking" 1 "filme:1"
ZINCRBY "stream:ranking" 1 "serie:1"
ZINCRBY "stream:ranking" 1 "filme:1"
ZREVRANGE "stream:ranking" 0 -1 WITHSCORES
ZSCORE "stream:ranking" "filme:1"
```

O filme fica com **2** visualizações e a série com **1**. `ZREVRANGE` mostra os mais assistidos primeiro, como no ranking de jogadores. Aqui contamos **visualizações**, inclusive repetições, porque o exercício não exige espectadores distintos.

### 4. Recomendação por tags e gêneros: conjuntos

Podemos agrupar os IDs dos conteúdos por gênero e por tag, usando `SADD`. Para este exemplo, o usuário 1 escolheu o gênero **ação** e a tag **aventura**:

```text
SADD "stream:genero:acao" "filme:1" "serie:1"
SADD "stream:tag:aventura" "filme:1" "documentario:1"
SADD "stream:usuario:1:generos" "acao"
SADD "stream:usuario:1:tags" "aventura"
SMEMBERS "stream:usuario:1:generos"
SMEMBERS "stream:usuario:1:tags"
SINTER "stream:genero:acao" "stream:tag:aventura"
```

A interseção retorna **filme:1**, o conteúdo presente tanto no gênero escolhido quanto na tag escolhida. É o mesmo raciocínio dos amigos em comum da aula. As consultas `SMEMBERS` recuperam as preferências; quem monta a consulta com as chaves correspondentes é a aplicação.

Esta recomendação usa apenas filtros por conjuntos, como pede o enunciado. Para outros filtros, `SUNION` reúne alternativas e `SDIFF` obtém os membros de um conjunto que não estão no outro.

### 5. Sessões e tokens temporários: hash ou string com EXPIRE

Para a sessão, usamos um hash como no exemplo `sessao:usuario:1309`. O token abaixo é apenas um **valor fictício para estudo**, não um mecanismo de geração de credenciais:

```text
HMSET "stream:sessao:token-estudo-1" "usuario" "1" "nome" "Carlos"
EXPIRE "stream:sessao:token-estudo-1" 1800
TTL "stream:sessao:token-estudo-1"
HGETALL "stream:sessao:token-estudo-1"
```

A chave associa o token aos dados da sessão e expira em **30 minutos**. A aplicação pode renovar o prazo com outro `EXPIRE`, seguindo o exemplo da aula.

Se for necessário guardar somente a associação entre token e ID do usuário, uma string também atende:

```text
SET "stream:token:token-estudo-2" "1"
EXPIRE "stream:token:token-estudo-2" 1800
GET "stream:token:token-estudo-2"
```

São duas formas de representar os dados temporários; não é necessário manter as duas para a mesma sessão. Redis armazena a associação e aplica a expiração, enquanto a aplicação cuida da criação e validação do token.

### 6. Notificações em tempo real: Pub/Sub

Como nos canais `geral`, `dev` e `teste`, podemos usar um canal para novidades e outro para as recomendações do usuário.

No **shell 1**, assine os canais:

```text
SUBSCRIBE stream:novos-conteudos stream:usuario:1:recomendacoes
```

No **shell 2**, publique as notificações:

```text
PUBLISH stream:novos-conteudos "Novo conteudo: filme:1"
PUBLISH stream:usuario:1:recomendacoes "Recomendacao para voce: filme:1"
```

O primeiro shell recebe as duas mensagens enquanto está inscrito. Isso atende à comunicação em tempo real do exercício pelo modelo de publicação e assinatura apresentado na aula.

## 16. Tutorial: Redis no Docker com o shell redis-cli

Esta parte adapta o ambiente para estudar em casa. **Docker é um complemento ao material**, que mostra instalação local com WSL/Ubuntu. Os testes no shell reutilizam os exemplos da aula.

### 1. Conferir o Docker

Tenha o Docker instalado e em execução. No Windows com Docker Desktop, use contêineres Linux. Os comandos com `\` para continuar a linha abaixo são para **Bash**, como no Linux ou no terminal Ubuntu/WSL; em outro terminal, você pode digitar o comando inteiro em uma linha.

No terminal do computador:

```bash
docker version
docker ps
```

Se o Docker ainda não estiver instalado, siga o [guia de instalação para seu sistema](https://docs.docker.com/get-started/get-docker/).

### 2. Criar o Redis com persistência

Execute uma vez:

```bash
docker volume create banco2-redis-dados

docker run -d \
  --name banco2-redis \
  -p 127.0.0.1:6379:6379 \
  -v banco2-redis-dados:/data \
  redis:7-alpine \
  redis-server --appendonly yes --appendfsync everysec

docker ps --filter name=banco2-redis
```

O Docker baixa a imagem se ela ainda não existir no computador. As opções significam:

- `-d`: deixa o servidor rodando em segundo plano.
- `--name banco2-redis`: define o nome usado nos próximos comandos.
- `-p 127.0.0.1:6379:6379`: publica a porta do Redis apenas no endereço local do computador.
- `-v banco2-redis-dados:/data`: mantém os arquivos de dados em um volume do Docker.
- `redis:7-alpine`: imagem da linha Redis 7 usada para este ambiente de estudo.
- `--appendonly yes --appendfsync everysec`: ativa o AOF com a configuração apresentada na aula.

O volume guarda os arquivos; o AOF registra as operações para recuperar os dados. Este ambiente local usa conexão **sem senha**.

### 3. Entrar no shell do Redis

No terminal do computador:

```bash
docker exec -it banco2-redis redis-cli
```

O prompt passa a ser semelhante a `127.0.0.1:6379>`. Agora você está no **shell do Redis**, equivalente ao papel do `mongosh` para MongoDB. O cliente já vem na imagem; não precisa instalar `redis-cli` no computador.

No `redis-cli`, digite:

```text
PING
SET nome "Joana"
GET nome
```

Os retornos esperados são **PONG**, **OK** e **"Joana"**. Não copie o texto do prompt junto com os comandos.

Para sair do shell, digite:

```text
exit
```

Isso encerra o cliente; o servidor continua rodando no contêiner.

### 4. Praticar os exemplos e abrir dois shells

Abra novamente `docker exec -it banco2-redis redis-cli` e execute os blocos do resumo ou da resolução. Listas e contadores acumulam alterações: repetir `LPUSH`, `RPUSH`, `INCRBY` ou `ZINCRBY` muda os resultados. Para refazer um exemplo do zero, remova **somente as chaves daquele exemplo** com `DEL`.

Para Pub/Sub, `WATCH` ou `BLPOP`, abra **dois terminais** e execute este comando em cada um:

```bash
docker exec -it banco2-redis redis-cli
```

Os dois shells acessam o mesmo servidor. Por exemplo, o primeiro pode executar `BLPOP fila:confirma-email 30` numa fila vazia, enquanto o segundo insere `RPUSH fila:confirma-email "aluno@ifsp.edu.br"`. O primeiro recebe o elemento e deixa de esperar.

### 5. Testar a persistência com o exemplo da aula

Dentro do `redis-cli`:

```text
SET cidade "São Carlos"
GET cidade
exit
```

De volta ao terminal do computador, reinicie o contêiner e reabra o shell:

```bash
docker restart banco2-redis
docker exec -it banco2-redis redis-cli
```

No Redis:

```text
GET cidade
```

O resultado deve continuar sendo **"São Carlos"**. É o mesmo teste de gravação, reinício e consulta dos slides. O reinício normal verifica a recuperação; não simula uma queda abrupta nem garante perda zero nessa situação.

### 6. Parar e continuar em outro dia

Saia do `redis-cli` com `exit`. No terminal do computador, pare o servidor:

```bash
docker stop banco2-redis
```

Para voltar a estudar:

```bash
docker start banco2-redis
docker exec -it banco2-redis redis-cli
```

Use `docker run` só na criação inicial. Nas próximas vezes, `docker start` reutiliza o contêiner e o volume com seus dados.

### 7. Conferir problemas comuns

- **Nome já em uso:** consulte `docker ps -a --filter name=banco2-redis`. Se for o contêiner criado neste tutorial, reutilize-o com `docker start banco2-redis`.
- **Porta 6379 ocupada:** na criação, troque o mapeamento por `-p 127.0.0.1:6380:6379`. O acesso com `docker exec -it banco2-redis redis-cli` continua igual, porque o cliente está dentro do contêiner.
- **Contêiner não está rodando:** execute `docker start banco2-redis`. Se ele encerrar novamente, consulte `docker logs banco2-redis`.
- **Shell parece estar esperando:** `SUBSCRIBE` escuta mensagens e `BLPOP` pode esperar por tarefas; use o segundo shell para publicar ou inserir um elemento.

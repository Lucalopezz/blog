# IPC, networking, and server process models

## Coordination crosses boundaries

Threads can exchange references because they share an address space. Separate processes must use an OS-mediated channel. Once processes live on different machines, the same idea gains failure modes: delay, duplication, reordering at the application level, partitions, incompatible versions, and independent crashes.

Moving a call behind HTTP does not preserve local-call semantics.

```text
local call: function(args) ─► return value / exception

remote call:
serialize ─► socket buffers ─► network ─► server queue
          ◄─ timeout? partial failure? duplicate retry? ──────
```

## Sockets

A listening TCP socket is bound to a local address and port. `accept` creates a new connected socket for each client; the listening socket remains available for more connections. TCP presents an ordered byte stream, not a message stream.

Important consequences:

- One `send` need not correspond to one `recv`.
- Reads and writes can complete partially.
- The application protocol must define framing: length prefix, delimiter, fixed size, or connection close.
- A successful write often means “copied to a local kernel buffer,” not “the peer application processed it.”

Unix-domain sockets offer similar local bidirectional semantics without IP routing. They are often appropriate between local daemons, a reverse proxy and application server, or a container and a host-side service.

## Serialization is part of the contract

Serialization converts in-memory values into bytes; deserialization reconstructs values under a schema or agreed format. JSON/HTTP favors debuggability and broad interoperability. Binary formats such as Protocol Buffers can reduce encoded size and parsing work, but “binary is always faster” is too absolute: payload shape, compression, copies, allocations, schema evolution, and implementation dominate many real workloads.

Never confuse an integer with its text representation:

```text
integer 1000 as unsigned 16-bit: 0x03E8          (2 bytes)
UTF-8 text "1000":              0x31 30 30 30    (4 bytes)
```

UTF-8 does **not** use two bytes for every character: ASCII code points use one byte; others use two to four.

Schema evolution questions:

- Can an old reader ignore a new field?
- Can a new reader handle a missing field?
- Is numeric range/precision preserved?
- Are timestamps, time zones, and nullability explicit?
- Is the operation idempotent when a timed-out request is retried?

## Server concurrency models

Three simplified designs recur in the videos:

```text
process per connection      thread per connection      event loop
isolation, high overhead    shared state, simpler flow many sockets, few threads
```

A modern server often combines them: a supervisor process starts several workers, each worker runs an event loop or a runtime scheduler, and CPU-heavy work goes to a bounded worker pool.

NGINX is a useful mental model: a master manages worker lifecycle; workers monitor many sockets through OS readiness APIs. It avoids one kernel thread per mostly-idle connection.

## Readiness versus completion

The video groups asynchronous I/O under one idea, but OS APIs differ:

- `select`, `poll`, `epoll`, and `kqueue` commonly report **readiness**: an operation is unlikely to block now.
- IOCP reports **completion** of submitted operations.
- Linux also has `io_uring`, which supports submission/completion queues for many operations.

In either model, the application needs a loop that associates events with connection state and makes progress without blocking the loop.

## Backpressure and boundedness

Queues absorb bursts; they do not create capacity. If arrival rate remains above service rate, an unbounded queue turns overload into memory exhaustion and terrible latency.

```text
arrival rate λ = 120 jobs/s
service capacity μ = 100 jobs/s
backlog growth = 20 jobs/s until something rejects, slows, or dies
```

Healthy systems bound queues and concurrency, expose overload, and propagate pressure upstream. Options include pausing reads, limiting in-flight requests, returning `429`/`503`, shedding low-priority work, or scaling consumers. The correct maximum comes from measured CPU, memory, database capacity, and latency objectives.

## Background jobs

A request path should enqueue work only if the user does not require its immediate result. The job system then needs semantics, not just a broker:

- at-most-once, at-least-once, or effectively-once processing;
- idempotency keys and deduplication;
- retry limits with backoff and jitter;
- visibility timeouts/leases;
- poison-message handling and a dead-letter path;
- observability of queue age, not only queue length.

“Exactly once” is usually a property of an end-to-end protocol and state transition, not a checkbox on the queue.

## A small local experiment

In one terminal:

```bash
python -m http.server 8000
```

In another:

```bash
curl -v http://127.0.0.1:8000/
ss -ltnp | grep ':8000'
```

Observe the listening socket, accepted connection, HTTP text protocol, and process owning the port. Then compare a Unix socket with `socat` if installed. This makes the abstractions in [[3.ProcessesAndIsolation]] concrete.

## The shortest useful model

At the bottom, a CPU repeatedly fetches, decodes, and executes machine instructions. An instruction may move data, perform arithmetic, compare values, or change the program counter. The program counter says which instruction comes next; registers hold the CPU's immediate working state.

```text
executable bytes in memory
        │
        ▼
program counter ──► instruction ──► registers / memory
        ▲                                  │
        └──────── next instruction ◄───────┘
```

Assembly is a human-readable notation for a processor's instruction set. It is not one universal language: x86-64, ARM64, and RISC-V have different registers, instructions, calling conventions, and machine encodings.

High-level code hides this detail, but does not remove it. A compiler or runtime must eventually produce instructions that the actual CPU can execute.

## Why an operating system exists

If every program controlled RAM, disks, network cards, and interrupts directly, programs would overwrite each other and every application would need a driver for every device. The OS centralizes this work and provides abstractions:

| Raw resource   | OS abstraction                                 |
| -------------- | ---------------------------------------------- |
| CPU time       | thread/process scheduling                      |
| physical RAM   | virtual address spaces and mappings            |
| disk blocks    | files and directories                          |
| network device | sockets                                        |
| device events  | interrupts, readiness/completion notifications |
| identities     | users, groups, credentials and permissions     |

The kernel is the privileged core of the OS. Applications normally execute in **user mode**; the kernel executes in **kernel mode**. Hardware enforces this distinction. User code cannot simply execute privileged instructions or access arbitrary physical memory.

## System calls

A system call is a controlled transition from user mode into the kernel. Examples on Unix-like systems include `read`, `write`, `openat`, `mmap`, `fork`, `execve`, and socket operations.

```text
application code
    │ calls libc/read()
    ▼
user-space wrapper
    │ syscall instruction + arguments
    ▼
kernel validates permissions and pointers
    │ controls device / filesystem / scheduler
    ▼
result or error number returned to user space
```

This boundary exists for safety and resource arbitration. It also has a cost: validation, mode switching, possible scheduling, and cache effects. Avoiding pointless syscalls matters in hot paths, but “syscalls are slow” is not a license to build a complicated cache without measuring.

`malloc()` is an important correction to the videos' simplified wording: it is normally a **user-space allocator API**, not itself a syscall. An allocator requests larger regions from the kernel occasionally, commonly through `mmap` or `brk`, then satisfies many small `malloc` calls inside those regions. See [[10.HeapAllocationAndFragmentation]].

## Interrupts, traps, and faults

These terms describe different ways normal execution is redirected:

- An **interrupt** is usually asynchronous: a timer or device signals the CPU. Timer interrupts let the kernel preempt a running thread.
- A **trap** is a deliberate synchronous transition, such as the instruction used to enter a syscall.
- A **fault** is raised by the current instruction, such as a page fault or division error. Some faults are recoverable. A page fault may simply cause the kernel to load or map a page and retry the instruction.

## Boot, in one accurate pass

On a modern PC, firmware (usually UEFI) initializes enough hardware to locate an EFI boot program. The bootloader loads the kernel and an initial RAM filesystem. The kernel initializes memory management, schedulers, drivers, and filesystems, then starts the first user-space process. On many Linux distributions that process is `systemd`, PID 1, which starts and supervises services.

GPT is a partition-table format; MBR is both an older partitioning scheme and, historically, a boot-code location. Neither is itself “the bootloader.”

## A practical trace

```bash
# Which executable will the shell run?
type -a python

# What kind of binary is it?
file "$(command -v python)"

# Trace file and process-related syscalls (Linux).
strace -f -e trace=openat,read,write,mmap,clone,execve python -c 'print("hi")'
```

The output connects a one-line program to executable lookup, dynamic libraries, memory mappings, and writes to standard output. Do not memorize every call. Learn to recognize which side of the user/kernel boundary owns a behavior.

## Misconceptions worth removing

- **“A 4 GHz CPU executes four billion useful instructions per second.”** Clock rate is cycles per second, not instructions per second. Instructions take different work; CPUs also pipeline, speculate, and execute multiple micro-operations per cycle.
- **“The kernel is the whole operating system.”** The kernel is central, but shells, system libraries, daemons, utilities, and package management are user-space parts of the operating environment.
- **“A syscall talks directly to hardware.”** Often it goes through several kernel subsystems, caches, queues, and drivers; it may not touch hardware immediately.
- **“Rebooting fixes the cause.”** It resets state. Before rebooting, inspect logs, process state, configuration, and service status so the failure remains explainable.

## When this matters

This boundary explains permission failures, blocking I/O, why containers share a kernel, why native binaries target both an ISA and an OS ABI, and why a runtime can cheaply schedule work in user space. Everything that follows builds on it.

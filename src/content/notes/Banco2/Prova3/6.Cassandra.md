## Antes de começar: rodar Cassandra no Docker

### 1. Criar o ambiente uma vez

Com o Docker em execução, rode no **terminal do computador**. Os comandos abaixo funcionam em uma linha no CMD, PowerShell ou terminal Linux:

```bash
docker ps -a
docker pull cassandra:5.0
docker network create cassandra
docker volume create banco2-cassandra-data
docker run -d --name banco2-cassandra --hostname cassandra --network cassandra -v banco2-cassandra-data:/var/lib/cassandra cassandra:5.0
```

Se a rede `cassandra` já existir, reutilize-a. Se `banco2-cassandra` já existir, use `docker start banco2-cassandra`, em vez de executar outro `docker run`. A imagem está fixada na linha 5.0 para este roteiro; a aula usa `latest`.

O volume guarda os dados para continuar depois. Este comando não usa `--rm`, que removeria o contêiner ao parar. O acesso será pelo próprio contêiner, sem publicar a porta no computador.

### 2. Esperar iniciar e abrir o cqlsh

```bash
docker logs --tail 60 banco2-cassandra
docker exec -it banco2-cassandra cqlsh
```

Na primeira inicialização, aguarde o servidor ficar pronto para conexões CQL na porta 9042. Se aparecer `Connection refused`, confira os logs e tente abrir o `cqlsh` novamente depois da inicialização.

Dentro do **cqlsh**, execute:

```cql
DESC KEYSPACES;
CREATE KEYSPACE IF NOT EXISTS loja
WITH replication = {'class': 'SimpleStrategy', 'replication_factor': 1};
USE loja;
```

Agora siga os blocos da [[7.Cassandra-Pratica|nota prática]]. Comandos CQL terminam em `;`; comandos `docker ...` são executados fora do cqlsh.

### 3. Parar e continuar outro dia

Saia do cqlsh:

```text
exit
```

No terminal do computador:

```bash
docker stop banco2-cassandra
```

Para retomar:

```bash
docker start banco2-cassandra
docker exec -it banco2-cassandra cqlsh
```

Espere a inicialização se necessário. No cqlsh, selecione novamente `USE loja;`. Para abrir outro shell ao mesmo tempo, repita `docker exec -it banco2-cassandra cqlsh` em outro terminal.

## 1. O que é Cassandra?

**Apache Cassandra** é um banco NoSQL distribuído do tipo **wide-column**, ou família de colunas. Guarda dados em tabelas com linhas e colunas, mas sua organização física gira em torno de **partições**.

- **Distribuído:** os dados são repartidos entre nós de um cluster.
- **Escalabilidade horizontal:** acrescentar nós permite distribuir armazenamento e carga; o resultado depende de uma boa distribuição das partições.
- **Replicação:** uma partição pode ter cópias em vários nós.
- **Alta disponibilidade:** réplicas permitem continuar atendendo quando parte dos nós falha, conforme o nível de consistência exigido.
- **CQL:** linguagem parecida com SQL, mas sem a mesma liberdade de consultas e relacionamentos.

Não confundir wide-column com um banco colunar analítico voltado a varrer colunas para relatórios. Aqui, a ideia central para a prova é **acessar poucas partições e ler linhas na ordem prevista**.

### Como os dados são gravados

De forma simplificada, uma escrita passa pelo **commit log** e pela estrutura em memória chamada **memtable**. Depois, os dados são descarregados em arquivos imutáveis, as **SSTables**. A **compactação** reúne arquivos e trata versões antigas e marcações de exclusão.

Esse desenho favorece muitas escritas, mas não torna qualquer consulta rápida. Ler tudo, filtrar depois ou acessar inúmeras partições continua tendo custo. Uma exclusão gera uma marcação chamada **tombstone**; ela não significa remoção física imediata de todas as cópias antigas.

As SSTables têm estruturas auxiliares de índice e filtros. O **Bloom filter** ajuda a descartar arquivos que certamente não contêm uma partição; um resultado positivo ainda precisa ser conferido. Uma leitura pode precisar combinar dados de várias SSTables, especialmente quando há muitas versões ou tombstones.

| Estratégia de compactação citada na aula | Ideia para revisão |
| --- | --- |
| STCS — Size-Tiered | Agrupa SSTables de tamanhos semelhantes; comum em cargas com muitas escritas |
| LCS — Leveled | Organiza em níveis para limitar sobreposição e favorecer leituras, com maior trabalho de reescrita |
| TWCS — Time-Window | Agrupa por janelas temporais; útil para séries temporais e retenção por TTL |

A estratégia depende da carga e da versão utilizada; a tabela resume as opções discutidas na aula, não todas as existentes. Compactação não significa mover automaticamente os dados para S3 ou outro armazenamento remoto: isso depende da solução e da configuração utilizadas.

## 2. Do modelo relacional para o modelo orientado a consultas

No relacional, podemos ter estas entidades normalizadas:

| Relação de origem | Chave e informações |
| --- | --- |
| Cliente | `id_cli`, nome, endereço, telefone |
| Produto | `(categoria, id_prod)`, nome, preço atual |
| Venda | `id_venda`, cliente, data/hora, total |
| ItemVenda | `(id_venda, nro_item)`, produto, quantidade, preço da venda |

**Neste material**, o produto é identificado por `(categoria, id_prod)`: o ID 1 aparece em várias categorias. Essa é uma característica dos exemplos, não uma regra obrigatória de todo cadastro de produtos.

Em Cassandra, começamos perguntando:

1. Quais consultas a aplicação precisa fazer?
2. Quais valores estarão disponíveis no `WHERE`?
3. Quais linhas precisam ficar juntas?
4. Em qual ordem serão lidas?
5. A partição pode crescer demais ou receber tráfego concentrado?

| Consulta da aula | Tabela projetada | Partição | Ordenação dentro da partição |
| --- | --- | --- | --- |
| Buscar cliente pelo ID | `cliente_by_id` | `id_cli` | Não há clustering |
| Listar produtos da categoria | `produto_by_categoria` | `categoria` | `id_prod` |
| Histórico do cliente | `venda_by_cliente` | `id_cli` | `data_hora DESC`, depois `id_venda` |
| Itens de uma venda | `itens_by_venda` | `id_venda` | `nro_item` |
| Relatório de um dia | `venda_by_data` | `data` | `hora`, depois `id_venda` |
| Vendas de um produto | `venda_by_produto` | `(categoria, id_prod)` | `data`, depois `id_venda` |
| Quantidade e gasto do cliente | `vendas_agg_por_cliente` | `id_cli` | Não há clustering |

**“Uma tabela por consulta” é uma orientação de modelagem.** Uma mesma tabela pode atender consultas compatíveis, como histórico completo do cliente, últimas vendas e histórico do cliente em um intervalo. Já vendas de todos os clientes em um dia pedem outra organização.

## 3. Keyspace, tabela e linha

O **keyspace** agrupa tabelas e tipos e configura a replicação dos dados. No laboratório:

```cql
CREATE KEYSPACE loja
WITH replication = {'class': 'SimpleStrategy', 'replication_factor': 1};

USE loja;
```

`replication_factor: 1` significa **uma cópia por partição**, sem redundância contra a perda do único nó que a armazena. Não significa uma partição nem uma tabela.

`SimpleStrategy` atende ao exemplo local de um nó. Em um cluster real, utiliza-se normalmente `NetworkTopologyStrategy`, configurada conforme os datacenters e a topologia. Particionar é **dividir** os dados; replicar é **copiar** as partições.

## 4. PRIMARY KEY: partição e clustering

A chave primária completa identifica uma linha. Ela é formada pela **chave de partição** e, opcionalmente, pelas **colunas de clustering**.

| Declaração | Chave de partição | Clustering |
| --- | --- | --- |
| `PRIMARY KEY (id_cli)` | `id_cli` | Nenhum |
| `PRIMARY KEY (categoria, id_prod)` | `categoria` | `id_prod` |
| `PRIMARY KEY ((categoria), id_prod)` | `categoria` | `id_prod` |
| `PRIMARY KEY ((categoria, id_prod), data, id_venda)` | Par `(categoria, id_prod)` | `data`, `id_venda` |

Os parênteses internos agrupam uma **chave de partição composta**. Nos dois exemplos com apenas `categoria` na partição, as declarações são equivalentes.

### Chave de partição: quais linhas ficam juntas?

```cql
PRIMARY KEY (categoria, id_prod)
```

Todos os produtos de `'Eletrônicos'` pertencem à mesma partição dessa tabela. Dentro dela, `id_prod` diferencia as linhas. O mesmo ID pode aparecer em outra categoria sem colisão.

O particionador calcula um **token** a partir da chave de partição; os intervalos de tokens e a estratégia de replicação determinam os nós responsáveis. Mesmo token não significa uma linha: todas as linhas da mesma partição compartilham o token. Tokens também não são IDs de nós nem uma ordenação alfabética das categorias.

```cql
SELECT token(categoria), categoria, id_prod, nome
FROM produto_by_categoria;
```

Essa consulta ajuda a observar o conceito em uma base pequena. Ela percorre a tabela e não representa o acesso pontual desejado em produção.

### Clustering: como as linhas ficam ordenadas?

```cql
PRIMARY KEY (id_cli, data_hora, id_venda)
```

- `id_cli` reúne o histórico do cliente.
- `data_hora` permite ordenar e recortar o histórico por período.
- `id_venda` desempata vendas do mesmo cliente no mesmo instante.

```cql
WITH CLUSTERING ORDER BY (data_hora DESC)
```

As mais recentes vêm primeiro **dentro de cada cliente**. Não existe ordenação cronológica global entre todos os clientes. Colocar `id_venda` antes de `data_hora` mudaria o padrão de leitura: o período deixaria de ser o primeiro recorte de clustering.

> [!warning] Uma chave incompleta pode sobrescrever dados
> Se a chave fosse somente `(id_cli, data_hora)`, duas vendas do mesmo cliente no mesmo instante teriam a mesma chave. Inserções com a mesma chave fazem **upsert**: atualizam os valores informados em vez de criar uma segunda linha independente.

## 5. Consultas compatíveis com a chave

Com `PRIMARY KEY (id_cli, data_hora, id_venda)`, o acesso esperado informa o cliente e depois um intervalo de datas:

```cql
SELECT * FROM venda_by_cliente
WHERE id_cli = 3
  AND data_hora >= '2025-02-01T00:00:00+0000'
  AND data_hora < '2025-03-01T00:00:00+0000';
```

O intervalo é **fechado no início e aberto no fim**. Assim, inclui todo fevereiro, sem depender de escolher o último milissegundo do mês. O fuso foi explicitado para tornar os exemplos reproduzíveis.

| Tentativa | Análise para as tabelas da aula, sem índices adicionais |
| --- | --- |
| Produtos com `categoria = 'Eletrônicos'` | Acesso à partição da categoria |
| Histórico com `id_cli = 3` | Acesso à partição do cliente |
| Cliente 3 e intervalo em `data_hora` | Recorte pela primeira coluna de clustering |
| Apenas intervalo em `data_hora` | Falta a partição; não é o acesso suportado sem filtragem |
| Apenas `id_venda` em `venda_by_cliente` | Não é uma busca pontual por essa chave; projete `venda_by_id` se necessária |
| Apenas `id_prod` em `venda_by_produto` | Falta `categoria`, parte da chave de partição composta |
| `ORDER BY preco_total` | O preço não é coluna de clustering dessa tabela |

**`ALLOW FILTERING` não corrige uma modelagem inadequada.** Pode permitir uma consulta com filtragem cara, mas não transforma a coluna consultada em chave de acesso eficiente. Para a prova, explique qual tabela atende ao padrão de consulta.

Índices secundários existem e têm usos próprios. Aqui, o raciocínio é projetar as chaves para as consultas conhecidas, sem depender de um índice para compensar cada mudança de requisito.

## 6. Desnormalização e ausência de JOIN

CQL não oferece `JOIN` nem integridade referencial por chave estrangeira como no modelo relacional. Por isso, `itens_by_venda` já guarda `nome_prod` e `preco_unitario_venda` junto do item.

- Ler os itens dispensa buscar cada nome no catálogo.
- O preço da venda pode ser diferente do preço atual do produto.
- O nome pode representar um **retrato histórico**, conforme a regra de negócio.
- A mesma venda aparece em tabelas por cliente, data e produto.

Essa duplicação reduz trabalho na leitura, mas exige manutenção na escrita. **Inserir em `venda_by_cliente` não atualiza automaticamente `venda_by_data`, `venda_by_produto` ou os contadores.** A aplicação precisa manter as representações e tratar falhas e reprocessamento. Não presuma uma transação relacional única entre todas elas.

Desnormalizar também não é copiar todas as colunas para todo lugar: guarde o necessário para cada consulta e defina o que deve ser histórico e o que deve acompanhar alterações do cadastro.

## 7. Desempenho: tamanho e distribuição das partições

Uma boa chave equilibra **localidade da consulta**, **quantidade de partições**, **tamanho de cada partição** e **distribuição da carga**.

| Escolha | Benefício | Limitação a avaliar |
| --- | --- | --- |
| Particionar produtos por categoria | Lista a categoria diretamente | Poucas categorias podem concentrar dados e acessos |
| Particionar vendas por cliente | Histórico em uma partição | Um cliente pode acumular histórico ilimitado |
| Particionar por dia | Relatório diário direto | Um dia muito movimentado ainda pode ser grande ou quente |
| Particionar tudo por uma constante | Parece facilitar uma lista geral | Concentra toda a tabela em uma partição |

Uma **hot partition** recebe tráfego desproporcional. Ter muitos nós não divide automaticamente as linhas de uma única partição entre eles; as cópias dessa partição continuam nas réplicas responsáveis.

### Bucketing: limitar o crescimento

Para um histórico muito grande, uma alternativa é separar por cliente e mês:

```cql
PRIMARY KEY ((id_cli, ano_mes), data_hora, id_venda)
```

Agora cada partição representa um cliente em um mês, como `(3, '2025-02')`. O mês deve incluir o **ano**, para não juntar todos os fevereiros.

A consulta precisa conhecer os dois valores. Um relatório de três meses consulta três partições e combina os resultados na aplicação. Bucketing limita o crescimento; não resolve sozinho um volume excessivo dentro de um único mês. A granularidade depende da carga real.

## 8. Tipos compostos e coleções

Os exemplos usam `INT` para identificadores, `TEXT` para texto, `DECIMAL` para valores monetários, `TIMESTAMP` para data/hora, `DATE` para data e `TIME` para hora. `UUID` e `TIMEUUID` são alternativas de identificação; UUID comum não representa ordem cronológica, enquanto TIMEUUID é baseado em tempo. Ordenar resultados ainda depende das colunas de clustering.

| Recurso | Significado | Exemplo da aula |
| --- | --- | --- |
| UDT | Tipo com campos nomeados e tipados | `endereco_type` |
| `FROZEN<UDT>` | Valor tratado como unidade nas atualizações | Substituir o endereço inteiro |
| `LIST<TEXT>` | Sequência ordenada que permite repetição | Comentários na ordem armazenada |
| `SET<TEXT>` | Elementos distintos, sem posição por índice | Comentários únicos |
| `MAP<INT, TEXT>` | Chave associada a um valor | Comentário identificado por número |
| `MAP<TEXT, TEXT>` | Atributos flexíveis, com chaves e valores textuais | Tamanho, cor, memória RAM |

**NoSQL não significa ausência de schema.** `colunas_dinamicas` é uma coluna declarada do tipo map. Acrescentar `'cor': 'Azul'` adiciona uma entrada ao map, não cria uma nova coluna CQL. O map da aula guarda valores textuais, inclusive atributos que poderiam ter outro tipo em uma modelagem específica.

Coleções são adequadas para conjuntos **pequenos e limitados**. Um histórico de comentários que cresce indefinidamente deve virar linhas em uma tabela, com partição e clustering adequados, em vez de uma lista sem limite dentro de uma linha.

## 9. Agregações e contadores

A aula usa `SUM`, `COUNT` e `GROUP BY`. Eles existem em CQL, mas o custo depende de quantas linhas e partições precisam ser lidas.

```cql
SELECT SUM(preco_total) AS total_gasto
FROM venda_by_cliente
WHERE id_cli = 3;
```

Essa consulta soma o histórico de **um cliente**. Já o agrupamento de todos os clientes percorre o conjunto de partições selecionado; funciona como demonstração na base pequena, mas pode ser caro em escala.

`GROUP BY` segue as colunas da chave primária na ordem definida, considerando as restrições por igualdade; não oferece o agrupamento arbitrário do SQL relacional.

Uma tabela agregada guarda o resultado antecipadamente:

```cql
CREATE TABLE vendas_agg_por_cliente (
    id_cli INT PRIMARY KEY,
    qtde_vendas COUNTER,
    total_cents COUNTER
);
```

- `COUNTER` recebe incrementos/decrementos por `UPDATE`, não atribuições comuns por `INSERT`.
- Colunas fora da chave em uma tabela de counters devem ser counters.
- `total_cents` representa centavos inteiros: `34990` equivale a R$ 349,90.
- Incrementar não é idempotente: repetir o comando conta novamente.
- Registrar uma venda não incrementa a tabela agregada automaticamente.

Para dados financeiros reais, o controle de reprocessamento e a reconciliação precisam ser planejados. O counter da aula demonstra agregação mantida na escrita, não uma solução completa de consistência contábil.

## 10. Replicação e consistência

O fator de replicação define quantas cópias há. O **nível de consistência** define quantas réplicas precisam responder a uma operação, por exemplo `ONE`, `QUORUM` ou `ALL`.

Com fator 3, um quorum corresponde a 2 réplicas. Exigir mais respostas pode reduzir disponibilidade quando há falhas e aumentar a latência. Exigir menos pode permitir leituras de uma réplica ainda desatualizada. Cassandra tem **consistência ajustável**; dizer apenas que “sempre é inconsistente” ou “sempre lê o último valor” simplifica demais o comportamento.

A regra é `QUORUM = floor(RF / 2) + 1`: com 7 nós no cluster e RF 4, são necessárias 3 **réplicas da partição**, não a maioria dos 7 nós. Em escritas com `ONE`, a confirmação espera uma réplica; isso não significa que a escrita seja enviada exclusivamente para um nó.

A aula apresenta **BASE**: disponibilidade como prioridade, estado que pode mudar com a sincronização e consistência eventual. Isso não elimina a possibilidade de exigir mais consistência por operação. Também não confunda a consistência entre réplicas com o **C de ACID**, associado às regras e invariantes das transações.

Na arquitetura sem mestre, um nó pode coordenar uma requisição e encaminhá-la às réplicas responsáveis. A comunicação de estado entre nós usa **gossip**. Na resolução usual de conflitos de células, vence o maior timestamp de escrita (**Last Write Wins**); ele é diferente da coluna de negócio `data_hora`. Relógios e timestamps incorretos podem afetar essa resolução.

Isso é diferente da consistência entre tabelas desnormalizadas: mesmo com replicação bem configurada, a aplicação ainda precisa gravar cada representação da venda.

### BATCH: agrupar escritas relacionadas

`BATCH` reúne `INSERT`, `UPDATE` e `DELETE`. Não é uma ferramenta para acelerar indiscriminadamente uma carga de dados nem equivale a uma transação SQL com rollback e isolamento global.

- Na mesma partição, as alterações têm garantia de atomicidade e isolamento.
- Um **logged batch** entre partições usa o batchlog para assegurar a conclusão eventual das mutações; durante a aplicação, outras leituras podem observar apenas parte das mudanças.
- Um **unlogged batch** entre partições pode ficar parcialmente aplicado em uma falha.
- **COUNTER BATCH** é próprio para contadores; não se misturam counters e escritas comuns no mesmo batch.

Por isso, gravar uma venda e incrementar seu counter não vira uma transação única apenas por usar `BATCH`. Essa distinção evita interpretar o agrupamento como uma garantia ACID completa.

## 11. Roteiro de resposta para a prova

Ao receber um modelo relacional e consultas, responda para cada tabela Cassandra:

1. **Consulta atendida:** “listar as vendas de um cliente por período, mais recentes primeiro”.
2. **Partição:** `id_cli`, porque o cliente será conhecido e suas vendas devem ser lidas juntas.
3. **Clustering:** `data_hora DESC, id_venda`, para intervalo, ordenação e desempate.
4. **Colunas necessárias:** total e demais informações exigidas, evitando JOIN na leitura.
5. **Custo e crescimento:** uma partição por cliente; considerar mês se o histórico crescer demais.
6. **Manutenção:** indicar quais tabelas recebem a mesma venda e como a duplicação será mantida.

> [!tip] Pergunta de revisão
> “Eu sei quais valores devo fornecer para localizar a partição? Dentro dela, as colunas de clustering estão na ordem que minha consulta precisa?” Se não conseguir responder, a escolha da chave ainda precisa ser revista.

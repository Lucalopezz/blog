# Compiling, linking, and loading

## The route from text to a process

For a typical C program:

```text
source (.c)
  └─ preprocess ─► expanded source
       └─ compile ─► assembly / IR
            └─ assemble ─► object file (.o)
                 └─ link ─► executable (ELF on Linux)
                      └─ load + relocate ─► running process
```

“Compiled” is not synonymous with “native executable.” Java compiles to JVM bytecode; TypeScript compiles to JavaScript; a JIT compiler translates hot runtime code to machine code. Always ask: **compiled from what representation to what target, and when?**

## Object files, symbols, and the linker

An object file contains machine code plus metadata. Some references are unresolved symbols: the compiler knows that `printf` exists with a certain signature, but not its final address. The linker resolves those references, lays out sections, and emits an executable or library.

Common sections in a native program:

- `.text`: executable instructions, usually read-only.
- `.rodata`: read-only constants.
- `.data`: initialized writable globals.
- `.bss`: zero-initialized globals; its size is recorded without storing all the zero bytes in the file.
- symbol, relocation, and debugging tables: metadata used by linking and tools.

The process's runtime stack and heap are created later; they are not giant pre-filled regions stored in the executable.

## Static and dynamic linking

Static linking copies the required library code into the final executable. Dynamic linking leaves references to shared libraries (`.so` on Unix, `.dll` on Windows) that a loader resolves when the program starts or when the library is first used.

| Static | Dynamic |
|---|---|
| easier to deploy as one artifact | smaller artifacts and shared physical pages |
| dependencies fixed at build time | dependency must exist at runtime |
| security update requires rebuilding affected binaries | compatible library update can fix many programs |
| can still depend on kernel/ABI behavior and external data | version/ABI mismatches can prevent startup |

“Static means fully portable” is false. A binary still targets an instruction set, executable format, OS ABI, and often assumptions about libc, DNS, certificates, locales, or files.

Inspect a binary:

```bash
file /bin/ls
ldd /bin/ls                 # shared-library dependencies on Linux
readelf -h -l -S /bin/ls    # ELF header, segments, sections
nm -D /bin/ls | head        # dynamic symbols
```

Do not run `ldd` on an untrusted binary; some implementations may execute its loader behavior. Prefer `readelf -d` when inspecting unknown files.

## Loading is not copying the whole executable

On `execve`, the kernel replaces a process image with a new one. It maps executable segments into the process's virtual address space, sets up the initial stack (`argv`, environment), and transfers control to an entry point. With dynamic linking, that entry normally enters the dynamic loader first.

Pages are generally populated on demand. The first access may fault, and the kernel maps a page from the filesystem page cache. This is why a large executable need not be read into RAM in one giant operation. See [[9.VirtualMemoryPagingAndSwap]].

## ABI versus API

An **API** is a source-level contract: function names, parameters, behavior. An **ABI** is the binary contract: register use, stack layout, symbol names, object representation, alignment, and calling convention.

Two libraries can present similar APIs but incompatible ABIs. This is the heart of many “DLL hell,” `undefined symbol`, and `LinkageError` failures. Source compatibility lets you recompile; binary compatibility lets an already-built consumer load the new library.

## Interpreters, bytecode, and JITs

An interpreter normally parses source into an internal representation such as an AST, often lowers it to bytecode, and executes that representation. A VM defines an abstract instruction set and runtime services. A JIT observes execution and compiles selected paths to native code.

```text
source ─► parser ─► AST ─► bytecode ─► interpreter
                                      └─ hot path ─► JIT native code
```

Real systems are hybrids. CPython compiles `.py` to bytecode before its evaluation loop runs it. JVM and .NET languages typically produce VM bytecode ahead of time and JIT it later. Go produces native code but links in a substantial runtime for scheduling and garbage collection. The implementation matters more than the marketing label.

## Build systems and package managers solve different layers

`make`, Ninja, Gradle, Cargo, and similar tools describe or execute build tasks. `apt`, `dnf`, and `pacman` manage system packages. npm, Maven, pip, Bundler, Cargo, and others resolve project dependencies. Some tools span more than one role.

The classic sequence:

```bash
./configure   # inspect this machine and produce build configuration
make -j       # build according to the Makefile
sudo make install
```

is historically important, but `sudo make install` bypasses the system package database and can make upgrades/removal difficult. Prefer a distribution package, a package-building recipe, or install under an isolated prefix when possible.

## Reproducibility

A dependency declaration says what is acceptable; a lockfile records a concrete resolution. Reproducible builds also depend on compiler versions, build flags, target platform, generated files, and sometimes timestamps or network inputs.

Practical questions during a “works on my machine” failure:

1. Which exact executable did `PATH` select?
2. Which runtime and architecture does it target?
3. Which dynamic libraries were loaded?
4. Are the dependency lockfile and build inputs identical?
5. Does the target provide the required OS ABI and external data?

Continue with [[7.RuntimesVirtualMachinesAndDependencies]] for how runtimes and project environments manage this complexity.

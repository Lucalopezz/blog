# Processes and isolation

## Program versus process

A program is passive data: an executable and its supporting files. A process is a running instance managed by the OS. It includes:

- a virtual address space;
- one or more threads and their CPU state;
- open file descriptors, current directory, and environment;
- credentials and resource limits;
- kernel bookkeeping such as a PID and scheduling/accounting state.

Starting two copies of the same executable creates two processes. Their code pages may refer to the same physical pages, but writable process state is isolated by virtual-memory mappings.

```bash
ps -eo pid,ppid,user,stat,comm,args
cat /proc/$$/status
ls -l /proc/$$/fd
cat /proc/$$/maps | head
```

`$$` is the current shell PID. `/proc` exposes kernel-maintained views; it is not a normal disk-backed directory.

## Creation on Unix: fork and exec

`fork()` creates a child whose initial process image resembles the parent's. The child gets its own virtual address space, but the kernel initially maps many pages to the same physical frames and marks them copy-on-write (COW). A write causes a private copy of the affected page.

```text
before write:
parent VA ─┐
           ├──► same read-only/COW physical page
child VA  ─┘

after child writes:
parent VA ─────► original physical page
child VA  ─────► copied physical page
```

`execve()` does something different: it replaces the current process image with a new program while retaining selected process attributes, including the PID and file descriptors not marked close-on-exec. Shells commonly `fork`, configure redirections in the child, then `exec` the requested command.

Windows primarily exposes process creation as a combined operation rather than the same `fork` API. Avoid turning historical performance comparisons into a timeless rule: current cost depends on OS version, workload, security tooling, address-space size, and creation path.

## Isolation is a mapping and permission property

Each process sees virtual addresses. Page tables translate them to physical frames and encode permissions such as read, write, execute, and user/kernel accessibility. Different processes can use the same numeric virtual address without referring to the same physical memory.

Isolation is not absolute:

- Shared libraries and file-backed mappings deliberately share physical pages.
- Shared-memory APIs map the same writable pages into multiple processes.
- Debugging facilities may permit one process to inspect another under strict rules.
- Kernel bugs or hardware side channels can violate intended boundaries.

The useful statement is: normal user processes cannot address one another's private mappings without an explicit OS-mediated mechanism.

## File descriptors are capabilities

On Unix, an open file descriptor is a small integer referring to a kernel object. That object might be a regular file, pipe, socket, terminal, or device. Standard input, output, and error conventionally occupy descriptors 0, 1, and 2.

```bash
printf 'alpha\nbeta\n' | grep beta > result.txt
```

The shell roughly does this:

```text
printf stdout ── pipe ──► grep stdin
grep stdout ── file descriptor ──► result.txt
grep stderr ──► terminal (unchanged)
```

This composition works because programs agree on byte streams and standard descriptors. A pipe is kernel-buffered and unidirectional. If its buffer fills, the writer normally blocks until a reader consumes data—an early example of **backpressure**.

## IPC choices

Processes trade easy failure isolation for explicit communication. Common inter-process communication mechanisms:

| Mechanism | Typical use | Important cost/risk |
|---|---|---|
| anonymous pipe | parent-child byte stream | one direction; lifetime tied to descriptors |
| named pipe/FIFO | unrelated local processes | byte-stream framing is yours to define |
| Unix-domain socket | bidirectional local client/server | serialization and protocol design |
| TCP socket | communication across hosts | network failure, latency, partial reads |
| shared memory | very high-throughput local exchange | synchronization and corruption risk return |
| signals | small asynchronous notifications | tiny payload, tricky handler constraints |

“Processes do not have race conditions” is false. They avoid accidental shared heap memory, but can race on files, database rows, shared memory, sockets, and external services.

## Signals and termination

`SIGTERM` requests graceful termination; a process may handle or ignore it. `SIGKILL` cannot be handled and lets the kernel end the process, but skips application cleanup. `SIGINT` is commonly generated by Ctrl-C. Graceful server shutdown usually means:

1. stop accepting new work;
2. signal cancellation to current work;
3. wait up to a deadline;
4. close/flush resources;
5. let an external supervisor force termination only after the deadline.

## Daemons and supervision

A daemon is simply a long-running background process, commonly managed today by a service supervisor such as `systemd`. Root is not part of the definition. Good services drop unnecessary privileges, use a dedicated identity, expose health/status, and let the supervisor restart them according to a deliberate policy.

Useful commands:

```bash
systemctl status sshd
journalctl -u sshd --since today
kill -TERM <pid>
ulimit -a
```

The same model reappears in containers and application runtimes: a parent/supervisor owns lifecycle, children/workers do work, and explicit channels coordinate them. See [[5.IPCNetworkingAndServers]] and [[12.ContainersResourcesAndPerformance]].
